# Recipe diagram audit

Audited all 26 individual Angular and React recipe pages. Changed 24 pages, added 13 purpose-built definitions, and retained the suitable existing diagram on two UI Kits pages. Every new figure sits after the introduction and before the ordinary application example. No second implementation figure was needed: existing workbench tables, recordings, inspectors, and code already expose those details.

“Add” includes replacing a redundant `hb-concept-diagram`. “Retain” means no new figure or Markdown edit. There are no unaudited recipe pages and no pages marked no-add without a retained figure. Existing headings, bookmarks, code, videos, images, and inline workbench panels stay in place.

The source paths below are repository-relative. `runtime/` and `server/` expand to `www/examples/quickstart/runtime/` and `www/examples/quickstart/server/`. React clients expand to `www/examples/quickstart/react/src/`; Angular clients expand to `www/examples/quickstart/angular/src/app/`. Each row names that framework's actual client. ## Evidence and verification

- Re-read all Angular and React recipe introductions and section structure, the source contracts behind each relationship, and the distinct Threadplane consumer implementations. Read Brian Love's January 2024 posts for short, direct prose and concrete first-person teaching style.
- The 13 new definitions use architecture, state, branching flow, and sequence diagrams. Each includes a title, caption, and full textual equivalent.
- Ran the actual `validateDiagram` function against all 13 definitions by transpiling the catalog and validator with the installed TypeScript runtime: passed. This checks IDs, participants, edges, and canvas bounds.
- Verified that each modified page references its intended definition exactly once and retains its existing code fences, headings, images, demo, and workbench tags. UI Kits is unchanged.
- Build, lint, framework tests, registry integration, and rendered responsive visual checks belong to the parent change's shared verification. No package code or SDK behavior changed in this slice.

## Accuracy boundaries

The decision diagram is a policy branch, not a claim of calibrated confidence. Predictions have no confidence score. UI selection and prediction acceptance are browser application actions. Local model preparation is separate from generation and does not promise offline application assets. Text persistence diagrams preserve neither tool calls nor durable approval ownership. The conflict versions are illustrative, and the server demo repository is in process memory. Public endpoint rejection paths cover identity/Origin, input, ownership, and admission; every gate must pass. No diagram adds an automatic write, retry, model fallback, or authorization grant.
