# Candidate browser integration design

Root review approved the integration and the two narrowly scoped fixture seams below. The final recovery-only observation refinement supersedes the broader intermediate stage proposal. These changes establish test evidence and retain all public signatures and default execution behavior. Actual pack, browser, and provider execution remain required.

Root-reviewed integration refinement, derived from the approved 2026-11-01 candidate acceptance design, Task 7.1–7.3, current Task 4/5 public APIs, artifact scaffold, existing HTTP/durable/package-host helpers, and B's declared observer/proxy interfaces. No implementation, central-config edits, test/build/install/runtime/network/DB/browser execution, or qualification claim. B's implementation is still independently owned; this document consumes its interface contract and does not review its intermediate implementation.

The capability's `serverRevision` is the current Ready session revision returned by the authoritative recovery read. The durable approval batch's `published_revision` belongs to an earlier publication step and may be smaller after finalization or later maintenance. Independently require Ready, the exact current session/capability revision, a positive batch publication revision no greater than that revision, and the genuine batch/member/interrupt joins. Do not equate the two revisions or assume a fixed arithmetic offset. Admitted generation/revision are a third, separately observed lineage.

## Recommended composition and alternatives

Use a candidate-only runner plus a candidate scenario owner around existing `withDurableCluster`/`withDotnetFixture` package-mode facilities. Keep actual server authority in the qualified packed NuGet fixture, actual public state/commands in six leaf consumers per framework, and evidence in parent-owned observer/proxy/DB/provider captures. Reuse API-neutral helpers unchanged only after adding their complete executable source closure to candidate qualification. No edits to frozen public consumers, legacy recovery controls, public package validators, or `package-pr-acceptance`.

Copying the entire durable fixture would duplicate lifecycle and package guards unnecessarily. Extending legacy live/public browser controls would break the frozen 0.8.3 closure. The candidate scenario adapter is the smallest route: it preserves existing worker guards and owns only new routing, UI, manifest and evidence policy. Where an existing helper lacks a required observation, add a narrow fixture-only seam after root review rather than infer evidence or change product behavior.

## Candidate UI and control contract

Create six statically selected leaf components per framework, mounted through an outer route selected before any hook/resource runs: chat, structured chat, completion, structured completion, UI chat, UI completion. Each directly imports its actual root-exported function and public recovery types. No duck-typed cast adapter that invents members, conditional hooks, private runtime import, seventh with-message public facade, or new root export. A presentation-only panel may receive narrowly typed display data/callbacks; each leaf must visibly call its own real facade methods.

Runner-owned immutable page configuration contains scenario/thread, principal, stable proxy run+read endpoint, observer scope URL, facade/schema/tool descriptors and completion input choice. Store only owned thread/config restoration data, never a pending token/snapshot/outcome authority. Known outcomes are entered through controls by the runner after reading observer-held actual results. Tools/system/schema/UI-kit identity remain stable across rerenders and cold pages.

Controls: explicit start/send/input; explicit authenticated recovery read; escaped pending names/IDs/arguments; one per-call choice of known JSON or unavailable; JSON text parsed deliberately so quoted strings retain whitespace/Unicode, objects serialize strictly and null remains null; one approve/decline/cancel selection per genuine interrupt; explicit submit; explicit fresh authoritative read; ordinary next generation; explicit New thread; visible finite negative actions for stale token, missing outcome/decision, ordinary resume/send/generate/setMessages/setState/config changes where the public facade exposes them. Disabled buttons alone do not test server/local rejection. Negative actions call real methods using previously captured genuine tokens or incomplete supplied options; never fabricate a pending snapshot or protected interrupt.

On read capture local `facade.recovery.revision` BEFORE request, call `getRecoveryConfiguration()` once, send its unchanged JSON body to POST `/threads/<encoded-thread>/native-session` with fixture principal authentication and exactly one `Hashbrown-Recovery-Version: 2`. Validate actual envelope shape/version/disposition/capability and positive equal server revisions; pass real snapshot to `restoreConversation(snapshot,{expectedRevision,structuredHistory:'strict'})`. Use a local request generation guard to discard stale responses after thread/config changes/unmount; stale guard never invents a new R. Reject V1/downgrade/malformed data before restore. No run, tool entry or optimistic transcript append during read/render/remount.

Build `ResumeConversationRecoveryOptions` directly: `batchId=pending.id`, complete ordered `outcomes`, browser-only entries absent/empty, genuine interrupt IDs only with approve `{status:'resolved',payload:{approved:true}}`, decline false, cancel `{status:'cancelled'}` without payload. ServerRevision comes from actual capability; UI never treats local batch token/recovery revision as server ownership.

Completion leaves need special ordering: fresh mount input is undefined; perform explicit restore before restoring any nonempty input control value. While actual pending state owns scheduling, set the same original input and observe no run (existing completion scheduling gate); do not mount with nonempty input or change system/tools/schema to fake suppression. After settlement, the unchanged input must not schedule another run. A separate explicit next-input action starts the ordinary generation. Focused actual browser assertions must catch a spontaneous mount/restore/input rerun. React input uses state; Angular input is a signal. Do not import internal reconciliation APIs.

UI leaves use the actual kit-created `{ui:[...]}` schema and one trusted exposed component with required props, not HTML. Assert React actual output/ui/rawOutput and rendered node; Angular actual public value and RenderMessageComponent. Structured terminal fixture responses must satisfy the exact schema captured in `getRecoveryConfiguration` and provider native schema field. No preserve-diagnostics shortcut.
