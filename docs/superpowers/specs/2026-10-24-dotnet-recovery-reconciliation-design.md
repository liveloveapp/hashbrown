# .NET browser recovery and operational reconciliation

## Goal and authorized scope

Extend the tested .NET AG-UI source recipe with authenticated recovery after browser reload or an acknowledged resume stream failure, and protected operational inspection and reconciliation of stranded effects. Preserve the durable checkpoint contract introduced by `2026-10-24-dotnet-durable-checkpoints-design.md`: server-selected versioned operations, complete-batch decisions, opaque token/generation ownership, pure preparation, committed dispatch markers, and at most one registered execution dispatch per batch.

The user authorized autonomous design, review, implementation, PR, merge and verification using agents. Routine design choices do not require another approval. No new dependencies are needed or authorized by this design. The implementation remains reusable recipe source under `tools/conformance/dotnet/Integration`, together with public core/React/Angular recovery APIs. It is not a new .NET package or a general durable chat-session service.

## Alternatives and decision

1. **Atomic runtime restore and checkpoint-scoped server snapshots — selected.** A read-only authenticated query returns server-owned history and current checkpoint disposition. An explicit API installs that history and fresh local interrupt ownership without executing anything. This keeps storage and authority close to the existing checkpoint and gives framework applications a direct recovery contract.
2. **Native recovery SSE through a bootstrap transport.** A fresh runtime could call `resendMessages`, with a one-shot transport returning a messages snapshot and interrupt outcome before switching to the ordinary endpoint. This introduces artificial generation/retry behavior, requires run-ID adaptation, and risks historical browser-tool execution. It is more complex than explicit restoration and is not selected.
3. **General conversation/event persistence.** A full service could resume every ordinary chat and stream, but requires broader admission, event sequencing, browser-tool lifecycle, retention and pagination contracts. This change persists only history associated with a confirmation checkpoint and its resumed response.

## Public client contract

Expose a documented `ConversationSnapshot<State>` using public types: a nonempty `threadId`, canonical native AG-UI `Message[]`, optional JSON-compatible shared `state`, optional complete `Interrupt[]`, and optional `configuredSystemMessageId` identifying the original configured system overlay. The server envelope has its own schema/version, checkpoint revision and operational disposition; those are distinct from the runtime snapshot. Never serialize the existing local `PendingInterruptBatch.id` as recoverable authority.

Expose `recovery: StateSignal<{ readonly revision: number; readonly required: boolean }>` and `restoreConversation(snapshot, { expectedRevision })` on `ChatRuntime`, and equivalent documented projections/methods on supported React and Angular chat facades. Completion facades that share this lifecycle must forward recovery safely rather than hide an operation needed to leave recovery-required state. Public framework signatures reference public core types, never internal `ɵ` types. Update public API reports and reference documentation.

Expose a pure synchronous `getRecoveryConfiguration(): ConversationRecoveryConfiguration` alongside restoration on the runtime and framework facades. The public configuration DTO contains optional current trusted `system`, owned native browser `tools` declarations, and owned `forwardedProps`. Derive these through the same request-building path and current request-response schema/UI flag used by ordinary generation; never include handlers, credentials or a synthetic run. This lets a fresh browser query compatibility without sending a probe generation or duplicating internal schema construction. Capture the local revision before reading this configuration and making the recovery POST; intervening configuration changes invalidate installation through the ordinary revision check. Public values are cloned/frozen JSON, and retrieving them performs no scheduling, network or effects.

The local revision invalidates asynchronous lookup results. Advance it whenever thread, committed conversation, accepted configuration/state writes, interrupt ownership or recovery-required disposition changes in a way that makes an earlier snapshot unsafe to install. It is not a database revision or a claim token. Applications capture the revision before lookup and supply it on restore. A mismatched revision rejects the entire operation, including a mismatch detected when an accepted action reaches its queued commit.

Restore is synchronous, atomic and idle-only. Reject while a generation, tool invocation, synchronous scheduling claim, resume claim, or thread transition is active. Replacing an idle pending batch or acknowledged-failure state is allowed when the revision matches. Validate and clone all input before changing anything: thread identity, canonical message IDs and roles, message/tool relationships, supported content, shared-state JSON, complete interrupt shape/expiry, and compatibility with the current response schema and registered browser tools. Validate structured assistant history through the existing schema/projection path. Invalid data leaves the old runtime unchanged.

Preserve trusted local system instructions, transport, schema, registered tool handlers and runtime options. Snapshot data cannot replace code, select a transport, install a tool, or alter the response schema. Restoration retires old attempt/interrupt ownership, clears obsolete errors and transient response metadata, installs canonical history/state, and creates a fresh locally owned batch when interrupts are present. Old batch IDs remain stale.

Preserve exact configured-system overlay identity across reload. Today each runtime generates a fresh overlay ID; restoring the old effective request verbatim would retain the old overlay and prepend a second one. The selected Hashbrown recipe uses its existing effective-request invariant: a configured system overlay is the first message. The recovery query carries `system: string | undefined` from current trusted application configuration. When present, the stored original input's first message must be a system message with exactly matching text; otherwise lookup returns 409. Return that first message's ID as `configuredSystemMessageId`. When the query has no configured system, return no overlay provenance. Core with a configured system requires provenance matching the first message ID and exact current configured text, adopts only that ID, strips only that first message from underlying committed history, and continues deriving overlay content from trusted configuration. Later system-option changes reuse the adopted ID. Do not search/remove arbitrary system messages by equal content. Custom transports must honor this prefix invariant or supply explicit provenance through their own supported integration; no new forwarded-properties wire field is introduced. Tests must demonstrate actual reload preserves the exact original effective request.

Restoration dispatches no scheduling action, makes no network request and invokes no browser tool. This also holds before the effect engine starts or restarts: installing a snapshot during initialization must not queue latent work that runs after startup. Historical tool calls remain history; incomplete executable browser-tool calls are rejected rather than reissued. Establish the restored baseline so a later new send does not reclassify historical calls as newly executable. A subsequent explicit `resume` or message action uses ordinary runtime behavior. Completion adapters that react to thread epochs must suppress their automatic input-send behavior for restoration; forwarding a method alone is insufficient.

## Server-owned recovery data

The existing record has only a request hash and operation descriptor; neither can reconstruct a conversation. Persist owned native serialized UTF-8 bytes/text of the original `RunAgentInput` with the checkpoint creation transaction before emitting interrupts. Do not store this request as PostgreSQL `jsonb`: nested JSON key normalization can change the existing fingerprint. Terminal snapshots likewise retain canonical serialization through an explicit bounded representation. Keep the original messages, tools, forwarded properties/schema and state required to reconstruct exactly the request against which approval was bound. Do not reconstruct privileged parameters from recovered browser messages.

Add separate bounded response storage for the checkpoint-associated resumed generation: canonical completed history, optional shared state and safe terminal metadata, plus a generation outcome (`NotStarted`, `Running`, `Finished`, `Failed`, `Interrupted`, or `Unavailable`). Effect state and generation outcome are independent. `Completed` means the registered executor returned; the model can subsequently fail or the final transcript may be unavailable.

Capture has its own explicit fenced owner: checkpoint ID plus the accepted claim token and generation, held only in a server-local capture handle. Every capture start, terminal persistence, failure observation and cleanup update conditionally matches that owner and its still-current capture authority. A successful effect transition to `Completed` does not remove the matching owner's right to store its subsequent final model output, but it also does not permit an older owner's writes. Fresh admitted claims replace capture ownership; stale wrappers whose preparation lease expired cannot overwrite a successor's generation outcome or transcript. Reconciliation retires capture authority as well as claim authority. A write rejected by this CAS is a stale no-op/conflict, never a reason to reopen the effect or overwrite the winner. Never expose the capture handle/token to the browser or operators.

The memory store implements the same contracts but remains process-local development storage. The PostgreSQL store survives process restart and multiple instances. Owned JSON/arrays are cloned at storage and response boundaries. Snapshots expose only the application's client-visible history/state and public interrupt fields, never operation parameters, claim tokens, registry internals or server tool state.

Keep a monotonically increasing server record revision for recovery-visible changes and reconciliation. This revision is independent of claim generation and independent of local runtime revision. A server snapshot schema version identifies DTO compatibility. Unknown versions fail closed.

## Terminal response capture

Capture the actual upstream AG-UI SSE through the endpoint result wrapper, without replacing upstream provider/hosting composition. Intercept the HTTP response body feature as well as stream writes so upstream `BodyWriter` output is observed. Deserialize with the installed native AG-UI serializer rather than adding a protocol dependency. A bounded incremental SSE observer must handle UTF-8 and frames split across writes, multiple frames in a write, disconnects, errors and cancellation. A small pure fold of supported native events builds canonical completed messages and shared state; unsupported/incomplete output yields unavailable history. Observe only a checkpoint-associated request, including upstream server-tool continuations within that request. Browser-tool continuations in subsequent HTTP requests are outside this bounded capture unless explicitly associated with the same checkpoint and fenced before accepting their output; do not accidentally create a general conversation service. Do not persist arbitrary raw events as replayable executable history.

Persist final canonical history and terminal generation metadata before forwarding the corresponding successful terminal event where the wrapper can enforce that ordering. No database transaction spans streaming or model work. If storage or observation fails, do not advertise a durable completed answer. Preserve the checkpoint effect marker and report a failed/unavailable generation outcome through bounded server-owned cleanup when possible. A process death can leave `Running`; recovery then reports interrupted/unavailable history rather than inventing a final answer.

Do not replay recorded SSE through core to restore history: historical tool-call events could execute browser tools. Recovery passes only a validated canonical snapshot to the restore API. Never fabricate assistant text to stand in for missing model output. Operational status is displayed separately from assistant history.

## Authenticated recovery endpoint

Provide an explicit opt-in endpoint builder with a required authentication/authorization policy and a server-owned scope resolver. Registration without the required security configuration fails closed. Production applications supply their real authentication scheme and thread ownership policy; test headers are not an authentication recipe.

Use a bounded read-only `POST /threads/{threadId}/recovery` query so the application can submit its current trusted configured system text, client tool declarations and forwarded request configuration, including Hashbrown response schema, for compatibility checks. The query does not submit authoritative history, operation parameters, claims or outcomes and never starts a run. Its name and docs must make its read-only behavior clear. Do not put large configuration or private history in URLs. Current local state need not match before hydration: restored state comes from the server snapshot.

Authenticate first, derive scope from the authenticated principal/application, and enforce thread access. Look up the latest retained checkpoint for that scope/thread, preferring its unresolved checkpoint when present. Bound lookup and response sizes. Return a versioned envelope containing server revision, effect disposition, generation outcome, expiry/lease information safe for display, and an optional restorable `ConversationSnapshot`. Use `Cache-Control: no-store` and avoid existence disclosure for wrong-scope and unknown identities.

Compare the supplied current browser configuration against a digest of the stored original request configuration, using a documented exact canonicalization for system text, tool order/declarations and forwarded properties/schema. Changed configuration fails closed with a compatibility conflict; never silently substitute a new configuration. Resolve scope/ownership first: wrong-scope/missing is a nondisclosing 404, and only an authorized existing record can produce a configuration 409. Returned canonical messages must recreate the original request fingerprint when a pending confirmation is resumed. State is restored but is not currently part of that fingerprint. Preserve message IDs/order, metadata/reasoning/activity links, tool order and fingerprint-significant JSON serialization; avoid normalization that silently changes them. Keep existing request fingerprint and complete-batch checks at admission as the authoritative final check; a successful lookup is not a reservation. Test the next actual browser POST against the original under the .NET serializer, including a real reload and configured-system ID. Do not replace ordinary resumed request admission with authority reconstructed from browser-selected operation data.

Recovery does not claim, release, renew or execute a checkpoint and does not invoke a model. Database failure returns unavailable rather than falling back to browser history. Distinguish unauthenticated/forbidden, missing or no-longer-retained, compatibility/stale conflicts, malformed query, and unavailable storage with ordinary pre-stream HTTP responses. No claim token appears in any response.

| Stored condition | Recovery behavior |
| --- | --- |
| Pending, approval unexpired | Restore original history and the complete public interrupt batch. |
| Claimed, preparation lease active | Restore history with busy disposition and no decision controls. |
| Claimed, lease expired, approval unexpired | Restore controls; a later explicit decision competes for a fresh claim. |
| Approval expired | Restore available history and expired disposition, without interrupts. |
| EffectStarted | Restore available history and unknown/in-progress disposition, without interrupts. |
| FailedAfterEffect | Restore available history and ambiguous-effect disposition, without interrupts. |
| Completed, generation Finished | Restore stored final canonical history, without interrupts. |
| Completed, generation failed/missing | Restore available original history; state that the effect completed and final answer is unavailable. |
| Declined or FailedBeforeEffect | Restore available history and terminal disposition, without interrupts. |
| Reconciled | Restore available history and the operator-recorded disposition, without interrupts. |

Two tabs can recover the same batch. Their fresh local IDs are unrelated and confer no server ownership. Existing claim admission allows one winner; the loser receives conflict, then explicitly refreshes recovery. A stale lookup or a lookup followed by expiry never bypasses current server validation. Recovery after an acknowledged failed stream uses the same thread but atomically retires the old local ownership; it does not automatically replay the approved decision.

The recipe uses the envelope's recovery disposition to disable both approval and new-message controls while the checkpoint is busy or its effect outcome is unknown. It offers explicit refresh, authorized operational reconciliation, or a new thread according to application policy. Restoring a transcript clears local recovery-required ownership so the snapshot can be displayed; that fact alone is not permission to start another action on the busy/unknown thread. Keep this gate in recipe/application UI policy without widening `ConversationSnapshot` into an authorization mechanism. Direct calls still face authoritative checkpoint validation. Recovery itself never schedules work.

## Operational inspection and reconciliation

Supply opt-in authenticated builders for bounded list, inspect and reconcile endpoints. Require a distinct operator authorization policy and a server-owned permitted-scope resolver. Derive operator identity from authenticated claims, never the request body. The fixture must exercise ASP.NET authentication and policies with fixture credentials; do not publish header-based arbitrary identity as production authorization.

List uses a fixed maximum page size and bounded scoped cursor/filter input. Summaries contain batch/effect identity, operation name/version where authorized, effect state, generation outcome, timestamps, generation/revision and reconciliation disposition. Inspection includes bounded audit history and safe diagnostics. Neither list nor inspect returns claim tokens; avoid exposing full request history or privileged operation arguments by default. An ordinary browser principal cannot promote itself to operator or choose another tenant scope through a body field.

Reconcile accepts an expected state, generation and server revision, a terminal observed outcome (`ConfirmedPerformed`, `ConfirmedNotPerformed`, or `Unresolved`), and bounded reason/evidence references. It never calls `Prepare`, `Execute`, a model, or a browser tool. It never changes a checkpoint back to `Pending`, issues new approval IDs, or provides a retry action. Any newly desired business action requires a distinct authorized workflow.

Use a short transaction locking the record, checking scope, permitted source state and all expected concurrency values, then inserting an immutable audit entry and applying the terminal resolution atomically. Audit records include authenticated actor, server time, prior state/revision/generation, chosen outcome and bounded evidence/reason. Advance revision and claim generation or otherwise retire existing claim ownership so late `FinishAsync` cannot overwrite reconciliation. Stale competing reconciliation/completion returns conflict without a partial audit or state change. Do not provide an audit update/delete endpoint.

Initially the only permitted reconciliation source states are exactly `EffectStarted` and `FailedAfterEffect`. Reject `Pending`, `Claimed`, `Completed`, `Declined`, `FailedBeforeEffect`, and already reconciled records. It cannot override active preparation, completed or declined outcomes. Represent the permitted source states explicitly in code and tests rather than accepting arbitrary strings.

**CAS cannot revoke execution permission already issued.** A worker paused after a successful dispatch gate can still invoke `Execute` later. Fencing protects future dispatch and stale bookkeeping, not already issued permission. A factual conclusion that a stranded action was not performed therefore requires externally verified owner quiescence and downstream evidence. Require an explicit bounded acknowledgement of that prerequisite for a stranded marker; it is operator evidence, not proof supplied by a timer. Keep unresolved as a legitimate terminal recorded outcome. No automatic timeout can establish non-execution or authorize replay.

## PostgreSQL schema, retention and limits

Migrate schema version 1 to 2 under the existing startup advisory lock and metadata row transaction. Add nullable original-request and terminal-snapshot columns, generation outcome, record revision and observation timestamps, plus an immutable reconciliation-audit table and indexes for scoped latest-thread lookup and bounded operational listing. Add explicit constraints for revisions, generation outcomes and permitted terminal reconciliation representation. Schema creation on an empty database installs the same final schema. Unsupported future versions fail closed.

Existing version-1 rows lack reconstructable original requests. Retain their dispatch safety and inspection behavior, return a truthful recovery-unavailable disposition, and never synthesize recoverable approval from a hash. Migration must neither reopen them nor rewrite their operation meaning. Concurrent startup/migration must not expose partially initialized storage.

Use explicit configurable limits with safe defaults: original serialized request 256 KiB; serialized terminal history 1 MiB; recovery query configuration 256 KiB; 2,048 canonical messages per original/terminal/restored snapshot; list page size 50 and hard maximum 100; reconciliation reason 2,000 characters; evidence reference 2,048 characters. Public snapshot response bounds follow its bounded original or terminal payload plus bounded envelope metadata, and inspection audit pages use the same pagination maximum. Check original-request limits before accepting a checkpoint; an oversized original request fails before any interrupt or effect. Terminal capture exceeding its bound produces an unavailable terminal transcript without losing the effect marker. Stream observation cannot buffer an unbounded response in memory. Cleanup uses bounded batches and separate transcript/audit deadlines.

Keep recovery retention explicit and bounded; snapshot retention may be shorter than safety/audit metadata retention. Purging private transcript bytes must not make old interrupts executable. Unknown/deleted IDs remain rejected. Never silently evict unresolved `EffectStarted` records to admit new work. Reconciliation can release an unresolved live slot only by terminalizing it; retained IDs remain consumed. Audit records are immutable while retained, have an explicit independent default retention (30 days), and retain the minimal identifying prior/result state without a cascading foreign key that silently deletes them during the existing ten-minute terminal cleanup. Apply bounded audit cleanup separately. Document that stored history/state may contain sensitive application data, database access controls apply, and recovery is limited to retained checkpoint-associated history.

## Cancellation provenance integration addendum

Recovery normalizes private cancellation provenance against the runtime's already-owned committed history, and only when the retained thread matches the current thread. Incoming private metadata is stripped; only exact same-thread owned echoes regain it through the existing cancellation reconciliation helper. Schema validation exempts only these proven markers, which remain canonical and outbound while staying outside structured/UI projections. Restore remains atomic and inert.

A cold runtime has no such ownership proof. Native requests retain cancellation text but strip private provenance, so .NET retained structured/UI histories containing that text can fail schema validation. Do not infer ownership from text, invent provenance, remove history, or change request fingerprints. Document this limitation; plain-chat cold recovery preserves the text visibly. Test actual runtime cancellation, same-thread restoration, forged/foreign provenance rejection, atomic failure, and cold plain-text visibility before implementation.
