# ATC B4 rollout follow-up design

Status: Proposed; implementation of new fault scenarios requires review of this written design. Human authorized the merge of #828 and continued readiness work, with production B4 disabled. Source requalification and read-only configuration assessment are proceeding under that authorization.

## Objective and authority

Freeze merged #828 source `a2f92a4f02ab1dfc38051a44e509afb439634793`; retain the old `6d414a3` experiments and source bindings unchanged. Keep published B4 0.15.7, dependency lockfile, runtime policy, lease timing, production project settings, production database, and production backend unchanged. A successful validation is evidence for a rollout decision, not enablement authority.

## Options

1. Recommended: qualify the new source locally and by complete artifact comparison; then add narrowly bounded managed-invocation timeout and disposable database-compute restart scenarios. Keep physical worker crashes, storage failover and unknown production capacity explicitly unqualified.
2. Repeat only existing owned-process probes: useful for source regression, but does not close the managed-platform gap.
3. Provider-coordinated physical host/storage failure: stronger realism, requires provider controls and separately authorized contact. Not part of this execution.

Use an isolated clean checkout of a2f92a4, install only the exact public lockfile with lifecycle scripts disabled, and run build/test/lint for core, OpenAI, atc-server and atc-shared, the real browser backend fixture suite, and the complete B4 build. Record all differences rather than treating a matching entrypoint as matching closure. Frontend and non-B4 function changes need their own tests even if the B4 closure is equal.

If the complete B4 function tree is identical, carry forward its existing hosted evidence explicitly as byte-identical runtime evidence, with old deployment IDs and source; do not claim a new a2 deployment was tested. Preserve original attempt ledgers; no silent reset or new unapproved load/spend envelope.

## Proposed aggregate hosted budget (requires this design’s approval)

Existing ledgers stay immutable at 99/120 load and 10/16 recovery reservations. The new scenarios are a distinct proposed envelope, not a reset or assertion that old caps authorize more traffic: at most **16 additional HTTP/model reservations in total**, allocated 6 timeout, 6 compute-restart and 4 rollback. Human written-design approval must include this explicit increment. Cumulative historical plus new upper bound is 125 reservations (109 already consumed plus at most 16); original phase ceilings remain unchanged. Every seed, conflicting request, failed/inconclusive attempt, retry and rollback chat consumes a reservation before dispatch. There is no automatic provider retry outside the counted transport; record SDK retries if unavoidable and do not claim HTTP count equals exact upstream spend. Keep the pinned 4096 output-token cap; sum of top-level request output caps is 65,536 tokens. That sum is not an actual billable-token ceiling or dollar estimate: retries or multiple provider steps can add usage. An agreed provider-spend limit and available usage observation are required before execution, and are still pending human input. No new sustained-load run is authorized by this budget; if the runtime closure changed, execute only affected existing probes within the new allocation or present a revised bounded plan before traffic.

One owned request at a time, at least 20 seconds between starts on each thread except the deliberately time-critical conflict check (one immediately after confirmed fault, maximum one per scenario). Requests have a 55-second wall-clock bound; each scenario has a 20-minute total bound including drain and >=75-second snapshots. Stop scheduling on first correctness/identity failure, unexpected throttle or budget/deadline exhaustion; preserve partial evidence. Inconclusive faults consume budget and cannot be retried indefinitely.

## Phase B: managed invocation timeout

Vercel documents platform termination after maxDuration. This is an invocation-timeout experiment, not proof of a physical worker SIGKILL. Use one new immutable dedicated-preview fault artifact copied from the exact normal output with ONLY `/api/run.func/.vc-config.json` maxDuration shortened to 1 second. Record that exact config diff and separate full-tree hash, never replace normal artifact provenance. Leave normal previews at their existing 60-second duration and default 30-second runtime lease. No source fault endpoint, fake model, provider delay service, or production setting change.

Validate project/team/name/preview target and isolated database before requests. Use fresh synthetic owned threads and real pinned model/schema/output cap, at most 2 fault attempts and 6 total request reservations from the aggregate ledger. Count every dispatched request, including failures and conflicts, before dispatch in the durable aggregate ledger. A naturally fast request that finishes before timeout is inconclusive, not a successful fault; never lengthen input or increase spend indefinitely to force a fault.

Capture actual Vercel invocation/request ID and supported timeout log/error evidence. A client-side abort alone is insufficient. On platform timeout, observe durable committed input/history and admission state; an immediate release is a valid graceful outcome and must not be labeled orphan recovery. Where a lease survives, require conflict wholly before database-clock expiry and a normal managed successor after expiry. Preserve all committed prefixes, exactly one canonical successor, provider-ID isolation, zero first post-EOF admission read, and unchanged complete state at least 75 seconds later. Stop on unexpected correctness failure; clean owned requests/pools. No draining others' deployments or deleting old evidence.

## Phase C: disposable compute restart

Neon's supported restart API suspends and starts one compute endpoint. A restart is not storage-replica failover. Execution requires authenticated management access plus independently verified exact project/branch/endpoint IDs proving that the compute is disposable, owned for this test, and unused by production or unrelated preview consumers. Current available environment has Vercel access but no Neon management key; a SQL connection string does not authorize the management API. Do not restart the existing shared preview compute as a shortcut.

Prefer an existing explicitly designated disposable compute; provision new paid resources only with a known approved budget. Use an empty synthetic-only database and distinct test role with fresh dedicated preview deployments, never production secrets or a data-bearing clone of a user/production branch. Record provider operation IDs and timestamps before and after a single restart. No retry of an uncertain mutation until operation state is inspected. Use at most 6 HTTP reservations from the aggregate ledger in this phase, including retry/conflict/error attempts, with the aggregate concurrency, pacing, 55-second request and 20-minute phase bounds. Keep runtime default lease behavior; disable automatic harness retries and record runtime retries separately.

Before the restart, prove a durable committed synthetic prefix, start a new owned invocation, and observe its active admission row and real provider/request identity. Only then trigger the single provider restart. Record driver disconnect/HTTP/platform outcome and the provider operation’s completion plus a fresh successful DB-clock query. If no active owner or interruption is proven, classify the run only as reconnect evidence. After recovery, inspect surviving lease state; require pre-expiry conflict if a live lease is observable, otherwise explicitly record that assertion untested. Dispatch the successor only after database-clock expiry or positively observed prior release. Prove committed-prefix preservation, one canonical successor and zero first post-EOF admissions plus >=75-second full-state snapshots. Stale-write exclusion is tested only if the old owner demonstrably resumes and attempts work; without that evidence, leave it untested rather than interpreting old-owner silence as fencing. Preserve expected outage responses and distinguish recoverability from uninterrupted availability. Bound rollback/close paths when connections die. No global prune, no deletion of audit rows, no claim of physical HA failover or exact rejected-write identity from generic cancellation.

## Phase D: operational rollout contract

Read-only metadata observed Oct29 confirms hashbrown-atc project/team, fluid compute, iad1, 60-second project function default; B4 cookie/database keys are preview-only and production has no ATC_CHAT_BACKEND key. Keep secret values out of output. Production requires independently verified dedicated production storage, stable shared cookie secret, TLS, identity and isolation; presence metadata alone cannot establish DSN correctness. These are preconditions to a later separately authorized enablement, not changes to make now.

Record production owner, initial concurrency/request-rate envelope, latency/error SLOs, provider daily/token budget and alert thresholds from human input; do not invent them from the 70-request preview sample. Observed preview results can guide a proposed envelope but cannot approve it. Current telemetry does not establish complete provider retry/cost counts; list this gap and use authoritative usage where available.

Rollback must promote a verified retained OpenAI artifact, not change only ATC_CHAT_BACKEND on a packaged B4 artifact (the ingress rejects mismatches). Before rehearsal, build the direct OpenAI output from the same clean exact source with no secrets, preserve its complete tree/hash/lock bindings and local isolated-artifact verification, then inspect the executable uploaded preview’s READY/project/team/config identity. Do not treat a B4 artifact with an environment toggle as an OpenAI candidate. Rehearse equivalent normal-preview B4-to-OpenAI routing only on a newly owned non-production alias with a recorded initial mapping, using at most 4 aggregate reservations. Verify fresh synthetic visitor requests reach each exact inspected deployment, valid expected AG-UI/schema/marker output, absence of new B4 state writes for the direct-OpenAI request, and no duplicate canonical B4 response. Record that existing B4 conversations cannot be transparently continued as durable B4 threads after rollback. Restore the recorded initial alias mapping, verify the service mapping, then remove the owned alias if it was created solely for this test. Never move production domains/aliases. Preserve the B4 database and audit rows for investigation; rollback is not state deletion.

Retention is not an online global prune: existing cleanup requires all B4 instances stopped and admission disabled. Test existing cleanup behavior on disposable synthetic local data; production needs an explicit offline maintenance/retention owner and schedule. Current 10-minute browser-call lifetime, 24-hour call-record retention and 24-hour thread admission are unchanged.

## Review, evidence, cleanup

New reusable harness behavior uses failing top-level tests first, TSDoc, no dependencies, meaningful stream/deadline/ledger/identity/cleanup regressions, affected build/test/lint, and independent source and actual-manifest review before hosted execution. Record exact source/artifact/function-tree/package/deployment/database bindings, all attempts, provider operations, actual assertions, limitations and incomplete cases. Read preview secrets only when needed into mode0600 inside mode0700 staging; redact boundaries, scan exact values in deliverables, remove after experiments. Keep a durable owned-resource inventory before each mutation: deployment IDs/targets, alias initial/current mapping, compute IDs/status, temporary credential paths, active requests/pools and child PIDs. On success or failure, close requests/pools, resume then terminate any owned stopped child, restore and verify aliases, remove the shortened-duration fault deployment by its exact owned preview ID, and suspend/remove only explicitly created disposable compute resources under their recorded ownership. Normal validated preview deployments may be retained as evidence with an explicit retained inventory; failed deletion/suspension is a cleanup failure requiring follow-up, not a true flag. Preserve provider operation receipts, audit rows and sanitized evidence. Verify temporary credential absence and all terminal resource states. Owned resources only; no original workspace/env edits or shared state pruning.
