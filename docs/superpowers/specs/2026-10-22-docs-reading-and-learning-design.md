# Hashbrown documentation reading and learning design

Make the documentation usable to read and navigate, then give new users a direct route to generating UI with their own trusted components. The first successful result in the Quickstart is a model rendering a component the developer explicitly exposes. React and Angular receive equivalent learning journeys using their native APIs.

## Decisions

- The Quickstart ends with a trusted component rendered from model output. The user selected this over beginning with text chat.
- The sidebar and article scroll vertically and independently on desktop.
- Migrations is the last documentation section and starts collapsed.
- Move basic concepts out of the long numbered Guide into Fundamentals.
- Preserve existing documentation URLs while changing navigation and content.
- Deliver this in focused increments: reading mechanics, information architecture, then the first learning journey. Treat additional production content as a prioritized backlog.

## Current experience

The site is a Next.js application in `www`. Documentation is stored separately for React and Angular in `www/content/docs`. Both SDKs share navigation generated by `www/src/components/menus/docs-menu.data.ts` and rendered by `DocsMenu.tsx`.

The navigation currently lists Getting Started, Migrations, Guide, Recipes, and Platforms. Guide contains eleven numbered topics, ranging from basic message concepts to the JavaScript runtime and Activities. This combines an introductory course with independent advanced guides. The menu does not expose several existing pages, including Shared Agent State, Interrupt and Resume, Transform Request Options, Choosing a Model, Prompt Engineering, and Ethics.

`SectionShell.module.css` gives the shell a viewport height and clips the grid. The article panel and navigation already declare vertical overflow. The reported scrolling failure needs browser reproduction and measurements of the grid, menu, panel, and their ancestors before selecting a CSS fix. Missing size constraints are a hypothesis, not a confirmed root cause. The shell is also shared with API and blog layouts, so any shared change needs regression checks there.

Article body text currently uses Fredoka at 15px. Heading sizes are relatively close together, many articles divide sections with horizontal rules, and the Quickstart includes optional middleware and API tables before a complete rendered example. The table of contents appears only on wide screens and fades when the article ends.

## Delivery boundaries

### Increment 1: Reading mechanics

Repair scrolling and move Migrations to the bottom as a collapsed disclosure. This is independently useful and does not depend on rewriting documentation. Keep other section names and article typography unchanged in this increment.

Desktop behavior:

- The site header occupies its own stable area above the available reading space.
- The sidebar and article each have a bounded scroll area. Scrolling one does not move the other.
- The final sidebar link and final article paragraph remain reachable in short windows.
- Long code blocks scroll horizontally without expanding the viewport or preventing article scrolling.
- Keyboard navigation can reach all links and the reading region. Focused links are not clipped out of view.

Mobile behavior:

- The article is the main reading scroll area; the closed sidebar does not consume width.
- The open navigation drawer has its own reachable, vertically scrollable content.
- Closing search or navigation restores scrolling, including when navigating to another article.
- Use the available dynamic viewport height so browser controls do not hide the bottom of the reading region.

Migrations behavior:

- Use a native disclosure or an equivalent keyboard-accessible button with correct expanded state.
- Start collapsed on every initial documentation load, including a direct migration-page visit. The page title and article remain visible when the sidebar group is closed.
- Do not auto-expand the group based on the active route. This keeps “collapsed by default” literal and predictable.
- Preserve the active migration link styling when the reader expands the group.
- Keep version links in descending order. Place the help link outside the documentation groups, after Migrations.
- Use the same disclosure behavior in desktop and mobile navigation. Cross-visit persistence of expansion is unnecessary.

### Increment 3: First generative UI journey

Rewrite both Quickstarts around one complete example. Use a `WelcomeCard` with two string props, `title` and `message`. This demonstrates model-authored props rendered by developer-authored UI without requiring tools, a database, an external data API, or a component library.

The reader sees the full path:

1. Confirm an existing React or Angular app and the required server runtime and credentials.
2. Install the exact packages needed for the example, separated by client and server responsibilities.
3. Create one server endpoint using the existing Hashbrown provider adapter and AG-UI SSE encoding pattern. Keep the API key and model choice on the server. Use a same-origin `/api/chat` path to avoid adding CORS setup to the tutorial.
4. Configure Hashbrown in the application with that endpoint.
5. Create the `WelcomeCard` using ordinary React props or Angular signal inputs.
6. Expose the component with `exposeComponent` and matching Skillet prop schemas.
7. Create UI chat using the framework's current API and render the generated UI with the framework's current renderer.
8. Send a fixed prompt from a button: “Welcome a developer to Hashbrown. Render a WelcomeCard with a short title and a one-sentence message.”
9. Show loading and error states, and describe the expected success result. The exact generated wording may vary; the visible result must be the exposed card.
10. Offer one next step: add a second component. Link tools, streaming props, and provider alternatives as related guides.

Every snippet names its file, includes necessary imports, and identifies where it belongs. Pick one documented server setup and provide complete integration instructions; do not imply a route file works in every React or Angular host. Exact APIs and the server setup must be checked against current package source before publishing.

Keep optional middleware, alternate providers, chat-history management, and comprehensive API tables out of the main path. Link to their guides and generated reference. The existing text chat APIs remain discoverable through Choosing an API and Fundamentals.

The tutorial explains the trust boundary beside the first component registration: the model selects among exposed components and supplies validated props; the application owns component implementation and behavior. Prop validation does not replace authorization for application actions.

Update the Introduction to lead toward this example. Update Choosing an API to begin with a small goal-based decision table and put its detailed capability matrix below. Recheck next-step links so the new reader journey does not send users back through the old numbered order.

## Editorial and visual direction

Use an outcome-first page pattern: purpose, prerequisites, minimal example, explanation, practical limits, next step. Guides explain one task; reference pages carry exhaustive options. Retain necessary lifecycle details, but introduce the visible behavior before internal terminology.

For a later visual pass, compare 16–17px system sans-serif body text with the current Fredoka body. Keep brand typography in headings and navigation unless the comparison exposes a specific readability issue. Aim for approximately 65–80 characters per prose line, around 1.6 line height, and a clearer size and spacing hierarchy for headings. Use heading spacing as the usual section separator; reserve horizontal rules for larger transitions.

Keep code formatting and horizontal scrolling predictable. Use filenames, short labels, and focused explanations. Avoid repeating every line of a snippet in a numbered list underneath it. Place optional details in disclosures without hiding required steps.

Keep the desktop table of contents available at the bottom of the article and constrain its own height on short screens. Offer an “On this page” disclosure above the article on narrow screens in the visual increment. Verify heading anchors and active-heading tracking against the actual article scroll container. Anchor navigation must preserve meaningful browser back navigation.

These visual changes require a layout comparison before implementation; they are not bundled into the initial scroll repair.

## Content priorities after the first journey

| Priority | Work | Intended result |
| --- | --- | --- |
| First | Surface existing state, interrupt, customization, and guide pages | Readers can find already-documented capabilities |
| First | Check Quickstart and Fundamentals against current APIs | Examples and recovery instructions agree with published behavior |
| Next | How Hashbrown works | One concise explanation of browser, server, provider, tools, schemas, and rendering |
| Next | Troubleshooting | Task-based recovery for endpoint failures, empty output, tool errors, schema failures, and cancellation |
| Next | Persistence and runtime lifetime | Explain what survives refresh, navigation, and runtime recreation; connect Threads, state, and interrupt behavior |
| Later | Testing and debugging | Explain deterministic checks, debugging facilities, and when live-model validation adds value |
| Later | Production patterns | Expand authentication, authorization, cancellation, observability, and accessibility using concrete examples |

The newer Activities page is a useful editorial model: it opens with user-visible behavior, compares related concepts, and then introduces the API. Threadplane provides useful examples of explicit prerequisites, complete named files, and guides connected to actual example source. Adopt those techniques without copying its multi-library navigation into Hashbrown's two-SDK structure.

## Validation

For reading mechanics, reproduce the failure in a real browser before editing CSS. Record viewport sizes, scroll heights, computed overflow, and which element receives scrolling. Verify sidebar and article scroll independently on a long page, reach both bottoms, and remain usable at mobile widths and with keyboard input. Include search and mobile drawer open/close sequences. Check API and blog routes because the shell is shared.

Write failing navigation tests before changing migration order, expansion behavior, or menu grouping. Keep top-level `test(...)` and arrange/act/assert spacing. Existing menu tests assert the old order and need intentional updates. Continue checking that every navigation destination exists for its SDK. Do not treat a CSS string assertion as proof of browser scrolling.

Validate Quickstart examples against package source and type-check complete examples using existing infrastructure where practical. Use deterministic renderer checks for component registration and rendering. A live-model smoke test is supplementary and must not assert exact prose or introduce a new mandatory credential requirement for ordinary tests.

After code changes, run `npx nx build www`, `npx nx test www`, and `npx nx lint www`. Use the route report where route or renderer behavior changes. Report warnings and any checks blocked by the environment. Do not add dependencies without asking.

## Completion criteria

- Desktop readers can independently scroll navigation and article through all content.
- Mobile readers can scroll both article and open navigation without a lingering scroll lock.
- Migrations is last and initially collapsed in both navigation presentations.
- Both SDKs have equivalent navigation with working existing URLs.
- The Quickstart produces UI using a trusted component through complete, verified code.
- The Introduction, Choosing an API, and next-step links support that journey.
- The repository retains the broader editorial backlog without presenting unfinished guides as available pages.
