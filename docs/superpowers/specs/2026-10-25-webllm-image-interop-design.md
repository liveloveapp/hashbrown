# Dependency-free WebLLM image input proposal

Status: implemented as a bounded opt-in adapter and deterministic browser/worker contract suite; no WebLLM runtime/model loading, native inference, or dependency changes performed. Builds on current injected structural engine ownership. Scope: PNG/JPEG/WebP user images only, explicit opt-in; text output, schemas and trusted UI retain their existing execution path. Native tools and audio/video remain unsupported.

## Recommended API and compatibility

Add `media: { images: { maxBytes?, maxPixels? }, resolve(part, { signal }), maxTotalBytes? }` to an image-specific overload of `experimental_webllm`. Require `images` even when empty. The resolver accepts AG-UI ImagePart only and returns `{ blob: Blob, dispose?: () => void | Promise<void> }`. The presence of this configuration is an application assertion that its loaded model supports images, not automatic detection or a model selector. Keep the existing model option for an already-loaded engine; never load/reload/unload one.

Do not reference ChromePrompt* public names in WebLLM signatures. Their names express the Chrome transport contract and audio union. Retain those exports unchanged. Extract small unexported generic image-source/MIME/limit/decode/cleanup helpers into a local transport module shared by the two adapters; Chrome keeps its existing wrappers and output bitmap lifetime. Do not export generic helpers from core index. If later shared across packages they would need the internal ɵ prefix, but this work does not require that.

Preserve the existing default public text-only request/engine contracts. Recommended type shape: add a defaulted user-content generic to `WebLlmRequest<TUserContent = string>` and `WebLlmEngine<TUserContent = string>`, using a role-discriminated message union so system/assistant remain string-only. Existing unparameterized uses still see strings. Define one `WebLlmImageContent` alias for `string | ({ type: 'text'; text: string } | { type: 'image_url'; image_url: { url: string } })[]`. The image overload requires `WebLlmEngine<WebLlmImageContent>` and a new `ExperimentalWebLlmImageTransportOptions` interface. Keep `ExperimentalWebLlmTransportOptions` and existing overload intact. This is preferable to widening every existing WebLlmRequest content field, which would break string-only consumers even when they never opt into images.

Use own mutable request arrays in the structural protocol: WebLLM mutates its own request during validation, and its published message types use mutable arrays. Do not pass readonly input arrays directly. Require assignability checks for actual .85 and .86 MLCEngineInterface and worker interfaces, plus a legacy string-only injected engine. TypeScript method parameter bivariance can accept narrower create methods. In the new image options interface, spell the engine create surface as a function-valued property, `create: (request: WebLlmRequest<WebLlmImageContent>) => ...`, rather than inheriting the legacy method-only check. Add a negative compile test rejecting a text-only engine in that overload and positive tests for actual runtime classes. Keep legacy engine method compatibility unchanged. Do not use casts to hide an incompatibility.

The naming/generic details may be refined during compile-only API tests. Mandatory outcome: text-only callers keep their current string API; opt-in callers have a precise WebLLM image request shape; no third-party import/dependency in production. All reusable/new public declarations get TSDoc.

## Order and request validation

Preflight the entire request before acquiring any resource. Reject tools and assistant tool history as today. Skip activity/reasoning messages as today. Keep system/developer concatenation and response_format mapping unchanged. Only user arrays can opt into images. Other roles with arrays, audio/video/unknown parts, malformed sources, and unsupported ordering return nonretryable FEATURE_UNSUPPORTED or INVALID_MEDIA before resolver/engine calls.

Accepted media shape is `[image, ...images, optional trailing text parts]`. Concatenate adjacent trailing text with `join('')`, preserving exact characters with no inserted separator, into at most one WebLLM text part. Preserve image order. Image-only content is allowed. Text-only arrays are normalized to a string only in the image-enabled mode. Reject empty arrays initially. Reject any image after any text part, including an empty text part: a predictable structural rule avoids hidden normalization. Thus `[text,image]`, `[image,text,image]`, and arbitrary interleaving are rejected, never silently reordered or split into different turns.

Why this restriction: .85 validation allows only one text part and legacy prompt serialization emits all images before text. .86 retains that legacy path; its newer artifact path is separate. A strict images-before-text contract works across both without depending on runtime internals. See [.85 validation](https://github.com/mlc-ai/web-llm/blob/v0.2.85/src/openai_api_protocols/chat_completion.ts#L402), [.85 layout](https://github.com/mlc-ai/web-llm/blob/v0.2.85/src/conversation.ts#L116), and [.86 layout](https://github.com/mlc-ai/web-llm/blob/v0.2.86/src/conversation.ts#L127).

## Resolution, bounds and encoding

Resolve every accepted source through the application callback, including inline data, URL and file handles. Never pass original URL/file input to WebLLM: always supply canonical `data:<mime>;base64,<encoded bytes>` built from the validated resolved Blob. No implicit fetch, object URL, canvas transcoding, resize or network fallback. WebLLM can consume HTTP URLs itself; using data URLs deliberately prevents that request-time network behavior. Model artifact loading remains application-owned.

Retain Chrome defaults: 10 MiB encoded bytes per image, 16 million decoded pixels per image, 20 MiB encoded bytes across complete media history. Add one bounded image count, `maxImages` default 8 per run, to cap pathological many tiny images; include it within the images policy rather than add a generic public framework. Validate all configured bounds as finite positive safe integers before resource work. Count repeated historical images separately; no caching or source deduplication initially. Limits bound encoded input and decoded dimensions, not exact GPU memory or model context tokens.

Reuse canonical source validation: nonempty data/url/file values; declared MIME optional but if present PNG/JPEG/WebP and matching resolved MIME; inline `data` requires canonical raw base64, not a data URI, with predecode length bound. Require nonempty Blob, supported MIME and exact resolved size limits. Use createImageBitmap on the Blob to validate decodability and positive safe-integer dimensions/product within maxPixels. For WebLLM close the temporary validation bitmap immediately after checking dimensions, while Chrome retains its bitmap for prompting. No ImageBitmap crosses the worker boundary. No HTMLImageElement or external DOM types in public signatures.

Convert bounded Blob bytes to base64 with a chunked routine (no `String.fromCharCode(...wholeBuffer)` spread) and check abort before and after async reads. Use canonical MIME in the generated data URL; omit image_url.detail entirely. Do not log/attach data URLs, base64, resolver secrets or full requests in measurements; report counts, byte totals, dimensions and MIME only.

Potential resource limitation: native createImageBitmap decodes before dimensions can be checked; this pixel guard does not prevent a decoder's transient allocation. Match the existing Chrome guarantee and state that accurately. Header parsers for every codec would be a separate scoped change, not a dependency or stronger guarantee invented here.

## Lifecycle and cancellation

Reuse raceTransportOperationWithAbort and the existing once-only acquisition/disposal stack, including late resolver/decode results after abort. Preflight first; claim activeEngines before asynchronous image preparation so concurrent sends on the same engine fail MODEL_BUSY and cannot race acquisition. Cancellation during preparation must not interrupt the engine (generation has not started), but it releases adapter ownership promptly; a late acquisition may only clean up and never call create(). Release on validation/resolution/encoding failure.

Obtain the prepared request inside the existing local stream start lifecycle so the response's cancellation/dispose path owns preparation. Use the stream's composed signal, not only the caller's original signal, so dispose without caller abort also cancels acquisition. The existing reader/worker drain behavior remains authoritative after create has begun: interrupt once, drain through done, retain activeEngines ownership until drain settles. Never call unload or resetChat.

Register resolved resource disposal before checking cancellation. Close each decoded image once even when decode resolves after cancellation. Dispose resolved resources on all terminal paths; keep them alive through generation/drain conservatively, although the encoded data URL no longer depends on their backing handles. Ensure success and failure cleanup cannot turn a cancellation into an unhandled promise rejection. Clear request/prepared references after drain to release bounded base64 buffers; cleanup callbacks must not retain entire requests. No public cleanup API is added.

## Material unresolved decisions and default disposition

- Select/download a real WebLLM VLM and runtime revision: defer to explicit later model choice. Implementable adapter/contracts do not require a download.
- Broad interleaved content or .86 artifact-only behavior: excluded initially; images-before-text rejects loss rather than silently rewriting semantics.
- Audio: excluded even though [.86 protocol](https://github.com/mlc-ai/web-llm/blob/v0.2.86/src/openai_api_protocols/chat_completion.ts#L395) has capability-gated audio. Image opt-in grants no audio support.
- Native tools: remain rejected. Their system/schema restrictions and terminal parsed calls require separate protocol work.
- API type assignability: resolve by compile evidence before implementation lands; keep legacy overload and generic defaults rather than widen existing consumers by assumption.

## Implementation review record

The public type slice passed independent spec and quality reviews. Core implementation passed spec review after explicit-null policy rejection, and quality re-review after replacing identity-keyed history maps with occurrence-indexed plans. Every historical occurrence resolves and counts independently, even when callers reuse the same message object. Default text and image protocol snapshots are captured by send before asynchronous acquisition; later caller mutations cannot change instructions, schema, tools or content already preflighted.

Core and both framework hosts retain application ownership of the injected engine. The new local image target runs only deterministic worker shims with generated media; a real VLM remains unqualified and requires a separate explicit model/download decision. See the implementation plan and `tools/conformance/README.md` for commands and evidence limits.

The new image API is implemented in source for a subsequent package release; published npm version 0.8.1 does not contain it. Mock contracts establish transport behavior only, and real VLM qualification remains pending.
