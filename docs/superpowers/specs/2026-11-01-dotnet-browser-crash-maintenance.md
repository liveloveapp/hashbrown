# Task 6 refinement: cold recovery after actual worker death

Status: independently reviewed and approved design refinement, 2026-11-01. This document defines the maintenance behavior required for the approved cold-recovery milestone. It supplies no executed crash, package, or browser qualification; those results belong in separate qualification records.

## Scope and verified motivation

The normative specification is `docs/superpowers/specs/2026-10-31-dotnet-pending-browser-recovery-design.md`, especially strict Ready/revision admission, inert recovery reads, durable consumed-decision/Started fences, no silent revision rebase, and default no DDL. Task 6 of the implementation plan requires real process restart/crash windows. The following source findings describe the implementation before this refinement.

I independently inspected the current source, rather than treating the prior preflight as authority:

- `PostgresNativeSessionBrowserRecovery.cs`: cold acquisition checks exact authenticated key, compatibility, retained Ready/ever-saved state and captured revision before allocating authority. It must retain those checks.
- `PostgresNativeSessionOperations.cs`: status reads expose/validate payload only for Ready; expired request authority in Owned remains Busy. Failure cleanup requires an unexpired matching lease, so a killed worker cannot restore its row, and a replacement cannot impersonate its cleanup.
- `PostgresNativeSessionJournal.cs`: ordinary warm acquisition has takeover logic; using it to make a cold crash test pass would defeat the separate cold admission guarantee. Row state, request token, generation, revision and claim_revision already provide the required fence.
- `PostgresNativeSessionMaintenance.cs`: maintenance selects retention-expired private rows only. It has no request-lease reconciliation. Existing SQL privacy purge is schema-wide and retains safety identities.
- `PostgresNativeSessionInvocations.cs`: HasDispatch includes dispatch_generation in any invocation state, admitted_generation on approval members or batches, and unpublished Pending batch captures in the current generation. It is intentionally stronger than a Started-only test. RemoveUncommittedCalls deletes only unrepresented Captured calls without approval membership.
- `PostgresNativeSessionApprovals.cs`: ReadValidatedApprovalSnapshot validates prior canonical/snapshot and durable publication/member evidence without creating execution evidence. Its all-generations Started check is conditional on row.State == Ready. A maintenance path validating an Owned row must deliberately enforce that prospective Ready invariant too. ReadApprovalSnapshot wraps the data into lease-bound execution evidence and is the wrong default maintenance helper.
- `NativeSessionContracts.cs`: MaintenanceBatch is 1–1000, default 100; default request lease is 30 seconds and private retention one hour. The current MaintainAsync XML describes purging only.

Thus a safe process death before any irreversible reservation can leave an otherwise usable retained pending snapshot Busy until privacy expiry. A cold read cannot repair that state under the approved contract.

## Approaches

1. **Recommended: extend trusted application-owned MaintainAsync.** Reconcile expired request leases under selector locks and the database clock, alongside privacy purge, then let a separate fresh V2 read observe the new disposition. This reuses the existing scheduler and schema, keeps reads inert, and gives safe crashes a usable path. It is a real documented maintenance behavior change and needs RED coverage plus review.
2. **Separate application-called crash-reconciliation API.** Similar transactional safety, but adds a public API/endpoint and operator/scheduling surface for an operation already fitting maintenance. Unnecessary for this milestone.
3. **Leave expired Owned Busy; require terminal operator retirement.** Safe and smallest code change, but fails the planned safe pre-reservation cold restart usability. It cannot support an unqualified Task 6 completion claim.

Do not reconcile inside ReadStatusAsync, expose maintenance to recovery clients, call warm acquisition as a fallback, or retry a losing cold request with a newer revision.

## Trusted maintenance authority and compatibility

A journal instance is application-owned and bound to a trusted model/native-format identity plus catalog identity through `_compatibility`. It is not bound to a single agent or authenticated scope. Therefore lease reconciliation is eligible only when the stored compatibility exactly equals this instance's `_compatibility`; it may service different agents/scopes/partitions sharing that trusted compatibility, provided each row's complete stored key is independently reconstructed and verified. Running one scheduler per compatibility identity is the application's responsibility. A different catalog/model registration's retained row stays unchanged and unavailable to this instance; do not decode/rewrite it using this instance's catalog. Existing schema-wide retention purge remains schema-wide, since privacy expiry cannot depend on a compatible binary surviving.

For a candidate that might become Ready, reconstruct NativeSessionKey using its actual constructor and trusted persisted key_data. Verify canonical KeyData equality and computed Id plus stored agent/scope/selector column equality. Every ordinal partition must survive. Use a finite raw key-data bound derived conservatively from NativeSessionKey's 32 partition and 1024-byte identity bounds before parsing; 1 MiB is a conservative ceiling for the existing canonical representation including worst-case JSON escaping. Do not trust a selector/scope alone, infer partitions from current request context, or create a fake request lease. Invalid same-compatibility key/evidence may only be fenced by locked stored id as Blocked; it must never become Ready or be used to address another row. Foreign compatibility rows are excluded before decoding and are not counted as work.

Maintenance cannot infer process death or external quiescence. Expiry withdraws further journal authority; an already Started native effect or already authorized publisher can remain in flight. Consequently only work before every dispatch/consumption fence can return Ready. All uncertain work stays fenced; operator terminal retirement/reconciliation still requires external quiescence acknowledgement, exact state/generation/revision CAS and existing audit. No new maintenance audit is required; maintenance must not forge an operator outcome.

## Candidate selection, locking and bounds

Preserve schema-version verification and a single short database transaction. Eligible candidates are the union of:

- existing retention-expired rows with private bytes remaining (including approval/invocation descriptors);
- retained rows of matching compatibility in Owned/Saved/Publishing with an expired request lease.

Lock selected parent session rows with FOR UPDATE SKIP LOCKED. Bound the **combined** selected session count by MaintenanceBatch, not separate full batches for each branch. Fetch the authoritative database clock after locks, then recheck expiration, state, compatibility and applicable predicates under those locks. A candidate predicate using clock_timestamp only narrows selection; it is not the final authority. Privacy expiry takes precedence whenever both clocks have expired. A combined deterministic expiry-event ordering with id tie-break is a reasonable default to avoid arbitrary preference between the two work kinds. Scheduler cadence, lock contention and backlog govern visibility; do not promise recovery exactly at lease expiry.

The bound applies to selected/mutated session rows; existing per-session descriptor budgets bound validation. It is not a claim that PostgreSQL scans at most that many physical rows, and no new index/DDL is proposed. Reuse existing catalog, raw request, payload and aggregate approval limits. No renewed lease, new authority token, retention extension or model/tool callback is permitted. Cancellation/database/schema errors abort the transaction and surface to the application scheduler. Only classified row-data validation errors become Blocked; do not classify infrastructure failure as durable corruption.

Return the number of distinct session rows actually transitioned or purged after recheck, at most MaintenanceBatch. A row eligible for both branches counts once. Repeated maintenance of already fenced or Ready retained rows returns zero and leaves generation/revision unchanged. Concurrent replicas skip locked rows and retry them on future passes; they cannot count or transition a row twice. Existing docs calling the result a purge count need to describe the widened meaning.

## Exact retained-lease transitions

Each actual retained-lease transition clears token, lease_until and admitted_request; increments generation and revision exactly once; preserves claim_revision, ever_saved, expires_at and exact payload bytes; and never changes invocation/approval epochs, decisions, result digests, publication revisions or safety identities. claim_revision remains historical claim lineage until a later legitimate acquisition sets it to that new claim. No capability is issued by maintenance.

| Prior state, retained and request lease expired | Additional condition                                                                        | New state                    |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------- |
| Owned                                           | Full existing HasDispatch is true                                                           | Blocked                      |
| Owned                                           | HasDispatch false, complete key/compatibility/evidence and prospective Ready checks succeed | Ready                        |
| Owned                                           | HasDispatch false, key or retained evidence invalid/unsupported                             | Blocked                      |
| Saved                                           | Any retained payload/effect condition                                                       | Blocked                      |
| Publishing                                      | Any retained payload/effect condition                                                       | PublicationUnknown           |
| Ready, Blocked, PublicationUnknown, Retired     | Any request lease value                                                                     | No retained-lease transition |
| Owned, Saved, Publishing                        | Request lease still active at locked DB clock                                               | No transition                |

For the safe Owned branch:

1. Evaluate the full existing HasDispatch for the original current generation under the lock. Approved, Declined and Cancelled consumption all fence, even if no invocation Started. Completed invocation dispatch_generation also fences. Unpublished current-generation approval captures remain fenced rather than deleted.
2. Validate the original retained snapshot and canonical admitted_request with ReadValidatedApprovalSnapshot under the original generation/revision, not a fictitious incremented row or lease. Require ever_saved implies non-null NativeJson. Never deserialize the actual native agent or run preparation/provider/native work.
3. Enforce the invariants a Ready reader will require: no Started invocation in **any** generation; if a current pending publication exists, it is genuinely Pending with no decisions/admitted generation/admitted revision; all bound members, descriptors, positions, browser IDs, catalog versions and settled historical browser-result digests remain valid. Validate the post-clear Ready view as well where existing helpers depend on row.State/admitted_request, using unchanged original epochs so validation cannot legitimize corrupt future epochs by incrementing first. Snapshot data containing consumed current pending evidence cannot become Ready even if its consumed epoch was corrupted away from the current generation.
4. Only after those checks, call the established RemoveUncommittedCalls for the validated prior snapshot. Preserve all previously published Captured calls and every approval-associated row. Do not delete captures before validation and then use their absence as evidence of safety.
5. Commit Ready with the exact prior saved payload, not the uncommitted incoming browser-result/decision suffix. Maintenance does not accept those results. A fresh explicit request must present them again against a fresh revision.

A previously never-saved safe initial Owned row may return Ready only under the same complete validation; its EverSaved remains false and it receives no browser-recovery capability. This preserves ordinary fresh-start/warm behavior without inventing a cold pending snapshot.

Saved is deliberately conservative: SaveAsync has replaced the prior opaque/public bytes, so expiry cannot reconstruct a previously published snapshot or assert successful terminal publication. Publishing becomes PublicationUnknown even when a test happened to see terminal bytes. No Completed disposition follows from lease expiry.

For retention expiry preserve existing purge/tombstone rules: Publishing/PublicationUnknown remains PublicationUnknown; Blocked stays Blocked; Owned with the complete fence becomes Blocked; other eligible rows become Retired. Clear private bytes and retained descriptors as before, retire approval rows/batches while retaining their consumed metadata/identity fences, and never reopen/reuse selectors. Do not shorten or extend parent/child expiry or bypass the child-first retention constraints. Lease reconciliation itself changes neither parent nor child expiry.

## What clients and old owners observe

If published pending state was revision R, a cold acquire produces Owned at R+1 (other genuine state transitions can advance further). Maintenance observes its actual current revision S and, if safe, commits Ready at S+1 and the next generation. An old R request still fails exact CAS; no retry loop substitutes S+1. A new V2 read can issue the fresh pending capability for S+1, and a later explicit complete submission can acquire exactly once. Pure reads before maintenance remain Busy; pure reads after blocked/unknown outcomes expose no snapshot/capability. Snapshot rows and effects are unchanged by both reads and losing submissions.

The old token is cleared and generation advances, so late Renew/Capture/Reserve/Start/Complete/Save/Authorize/Finalize/Cleanup calls fail. Do not claim a previously authorized external effect or terminal write is stopped by that fact. Concurrent renewal versus maintenance is decided by the locked database-clock check; a still-valid owner that renewed first remains active, while an expired owner cannot resurrect its lease.

Suggested summary: “Runs bounded maintenance, preserving selector and effect fences; the PostgreSQL journal also reconciles expired request authority before purging expired private bytes.” Add returns/remarks covering count, compatible-registration scheduling, nonexecution, database clock, bounded batches and cancellation/backlog. Describe PostgreSQL behavior specifically so a custom journal is not accidentally claimed to implement automatic crash reconciliation merely by implementing the existing interface; incapable/declining optional recovery journals must still fail closed.

## Test-first proof inventory for root implementation

Use top-level test with arrange/act/assert, genuine durable published snapshots, isolated real PostgreSQL schemas and independently started processes from withDurableCluster. Current http-fixture.stop already sends actual SIGKILL and awaits exit; record PID/exit signal and barrier evidence. Do not substitute cancellation, normal disposal or thrown exceptions for process death. No warm POST may repair a cold crash. Use the existing test-only lease-expiry control after death, preserving payload retention; it models DB expiry deterministically, not waiting a guessed wall-clock interval.

First make the test-only FixtureNativeJournal implement/delegate the real optional browser-recovery interface, count attempt/success separately, and add an after-successful-cold-acquisition barrier. Keep an intentionally incapable fixture for decline coverage. Existing before-decision-reservation and decision-admitted barriers already surround actual reservation; dispatch/save/publication barriers already surround real authority transitions. Expose real MaintainAsync and complete read-only DB observation for browser-only native fixtures too: the current maintenance endpoint and approval inspection are inside nativeApprovals. No synthetic pending authority or fake journal.

1. **Mixed, pre-reservation SIGKILL.** Publish genuine mixed state; V2 read captures R; explicit complete results plus real decisions claim ownership and stop at before-decision-reservation. Observe Owned, exact incremented revision, pending/unconsumed batch, zero preparation/provider/effect increments. SIGKILL, await death, expire only lease, read Busy without row changes. Run real maintenance on independent worker: expect one transition to Ready, preserved payload/epochs, cleared admitted_request, next generation/revision. Current source should fail here (count zero/Busy). Old R submission remains409 with zero changes; a separate fresh V2 lookup yields a fresh capability and one explicit submission completes. Exercise both known/unavailable browser outcomes on separate legal cases.
2. **Browser-only after-acquire SIGKILL.** Same shape using new post-acquisition barrier, no artificial protected batch. Prior opaque/public bytes survive exactly; admitted result suffix never becomes saved history through maintenance. Fresh explicit completion works once.
3. **Consumed before Started.** Separate Approved/Declined/Cancelled real batches stop after decision-admitted; confirm consumed epochs, Captured invocation and zero effect. SIGKILL/expiry/maintenance gives Blocked and V2 UnknownEffect, no capability. Verify retained decision/browser-result digests unchanged and no redispatch or provider call from stale/fresh retries. This is the decisive negative for a Started-only implementation.
4. **Started and persisted effect.** Kill separately after dispatch marker commits but before handler, and after persistent effect but before save/settlement. Assert persisted effect counts 0 and 1 respectively; both stay UnknownEffect with original epochs/markers and zero redispatch across repeated reads/maintenance/restarts. Add an explicit after-effect barrier if needed; a process-local counter is not durable evidence.
5. **Save/publication.** Kill after-save-before-publication -> Blocked; publication-authorized and before-publication-finalization -> PublicationUnknown. Never infer Completed or a pending capability. Saved payload remains until privacy expiry. Hold a separate live late owner/receipt past expiry+maintenance and prove old completion/save/publication calls lose. SIGKILL tests alone cannot exercise a callback from a dead process.
6. **Active lease and races.** Maintenance before expiry is a no-op including lease/token/generation/revision/payload/counters. Renewal first versus maintenance first follows parent lock and DB clock. Two maintenance workers transition a row once. Two fresh submissions of a newly read revision have one winner, including identical transcript losers; never count attempts as successful acquisitions.
7. **Privacy, bounds, idempotence and invalid evidence.** Combined eligible count never exceeds configured batch; process remaining backlog in later passes. Retention dominates simultaneous lease expiry; unknown tombstones survive byte purge. Unpublished captures, all-generation Started corruption, future/foreign epochs, invalid keys, unsupported snapshot/native JSON, missing/mismatched member/binding/result evidence fail closed and never run callbacks. Test legitimate settled historical evidence still permits safe recovery; otherwise overblocking can hide as safety.
8. **Cross-registration/partition ownership.** In one schema use compatible rows with distinct full keys and an incompatible catalog/model registration. Instance A safely reconciles its matching rows without altering B's retained Owned/Saved/Publishing rows; B can reconcile its own rows. Schema-wide privacy purge still removes expired private bytes. Key-column/id/partition corruption cannot produce Ready. Test exact parent/child retention remains unchanged and trigger constraints still reject outliving children.
9. **Read purity and regression.** Compare all relevant DB fields around repeated V2 reads before/after maintenance and around stale losers. Count maintenance invocation separately. Run established warm native-only/browser/mixed, failure-cleanup, retention and operator-reconciliation cases; behavior change is only explicitly invoked maintenance's new expired-authority disposition. Exact reserved unavailable marker remains after accepted save, another fresh process and another recovery read.

Record independent acquisition attempts/successes, reservation, native preparation/deserialization, model HTTP, persisted native effect, save/publication, status reads and maintenance calls. Do not report a declaration-only server “browser handler = 0” constant as evidence of a browser handler not running: real client-handler proof belongs to Task 7 browser consumers. Counters needed after worker death must live in the durable database/stable model router or be captured before kill with matching database/barrier evidence.

Expected first RED is actual expired Owned remaining Busy after genuine maintenance, not missing optional-interface plumbing, missing fixture routes, package mismatch or unavailable PostgreSQL. Root should run the plan's existing runtime targets only after focused tests exist, then independently review source/spec invariants and all failure/warning evidence. No numerical pass/acceptance claim is made here.

## Review decisions and remaining limits

Recommended defaults requiring no routine user question: existing trusted maintenance entry point; compatible-instance lease eligibility; schema-wide privacy purge; one combined row budget; fail-closed Blocked on invalid compatible evidence; preserve exact saved bytes until retention; no fabricated lease; claim_revision unchanged by maintenance; no new DDL/API/dependency.

Real design risks to review: prospective Ready validation must not skip the validator's state-dependent Started rule or validate against incremented epochs; catalog identity is part of compatibility but not an authenticated per-agent key; foreground/background lock order must remain parent-first; a compatible instance with intentionally smaller limits can safely block a row that a larger-limit instance could have restored, so deploy consistent options; mixed source-version behavior is not solved by schema compatibility; row-budget boundedness is not a DB query-latency guarantee. These require precise tests/docs, not a weakened cold CAS or automatic effect retry.
