# Put Jev in front of the model

"TypeSafe Jev API" almost certainly means **Jev, the first "System One" decision model from TypeSafe AI**, launched in early access on 2026-09-15 and reachable through Vercel AI Gateway from 2026-09-21 ([Vercel changelog](https://vercel.com/changelog/ai-gateway-now-supports-typesafe-clients-and-http-api-for-jev); [Let's Data Science](https://letsdatascience.com/news/typesafe-ai-launches-jev-decision-model-889a38c0)). The phrase is not a mishearing: Jev is a real product from a company literally named TypeSafe. Jev does not write text or UI. You send it a `state` plus a map of typed questions (choice, score, yes/no "noul"), and it returns probabilities in roughly 100 ms for **$0.042 per million input tokens, with output free** ([Promptfoo](https://www.promptfoo.dev/docs/providers/typesafe/); [StartupHub](https://www.startuphub.ai/news/typesafe-jev-model-kills-chat)). Its generative-UI use is selection, not authoring: Vercel's json-render added an experimental mode in which Jev picks app-built, fully propped component candidates and places them in a tree ([json-render docs](https://json-render.dev/docs/jev)). That is close to Hashbrown's "only the components you expose" premise, but it bypasses Hashbrown's real differentiator, the streaming Skillet parser, because Jev neither streams nor fills props. The recommendation for Hashbrown is therefore not a new rendering format but a **non-streaming "decision" sibling of structured completion**: compile a Skillet object of enumerations, booleans and small bounded numbers into Jev questions and return a typed value with confidences. In atc, the strongest demo is a **router in front of the LLM**: one sub-second Jev call per submit that either applies a natural-language map filter instantly or, at low confidence, hands off to the existing streaming assistant. The neighbouring specs (A2UI, json-render, MCP Apps, OpenUI, AG-UI, Standard Schema) are worth a separate, larger interop track, and most of the leverage there sits in a small core change: stop discarding AG-UI ACTIVITY events.

## Jev is a classifier with typed answers, not a UI generator

The identification is high confidence. An exact-phrase search returns TypeSafe's Jev almost exclusively, the launch landed a month before the remark, and the Vercel changelog names the product "TypeSafe clients and HTTP API for Jev" ([Vercel changelog](https://vercel.com/changelog/ai-gateway-now-supports-typesafe-clients-and-http-api-for-jev)). TypeSafe AI is unrelated to Typesafe Inc., the Scala company now called Lightbend. A search of the Hashbrown repo and its GitHub issues found no prior mention of Jev, TypeSafe AI or json-render, so the developer should still confirm the reading, but no alternative fits as well. The runners-up, json-render itself and Google's A2UI, are already covered below, and Hashbrown's own design docs name A2UI and MCP Apps directly when they mean them.

TypeSafe describes Jev as "the first System One model": you supply state as text or JSON, ask typed questions, and get structured answers with "no text generation, no parsing" ([TypeSafe docs](https://docs.typesafe.ai/introduction)). The native wire API is a single endpoint, **`POST https://api.typesafe.ai/v1/systemone`**, with a bearer key. The body is `{ model, state, questions }`, where `questions` is a map from your own IDs to typed questions; the IDs are never sent to the model ([TypeSafe API reference](https://docs.typesafe.ai/api.md)). Three question types matter for UI. A **choice** question takes up to **255 options** as a record of option to description and returns `choice`, a `probabilities` map summing to 1, and `confidence`. A **score** question takes 2 to 10 ordered levels and returns a probability-weighted `score` that can fall between levels. A **noul** question returns a single probability that a statement is true, with no confidence field. A fourth type, `box`, returns an image bounding box on Jev 1.14+ behind a "danger zone" header ([AI SDK TypeSafe provider](https://ai-sdk.dev/providers/ai-sdk-providers/typesafe-ai)).

Four wire surfaces exist and they differ in small, annoying ways. The native API says `noul` and uses snake_case usage fields. Vercel AI Gateway's **`/v1/evaluate`** renames `noul` to `boolean` with a `probability` field, uses camelCase, and returns a per-call cost (the docs example costs **$0.00001155 for about 275 input tokens**) ([Vercel Decision docs](https://vercel.com/docs/ai-gateway/modalities/decision)). Gateway also hosts a TypeSafe-compatible `/typesafe/v1/systemone` that keeps native field names and accepts Vercel OIDC tokens ([Vercel TypeSafe API docs](https://vercel.com/docs/ai-gateway/sdks-and-apis/typesafe)). Finally, the AI SDK exposes **`experimental_decide`**, which needs `ai` 7.0.128+; the older name `experimental_evaluate` survives only as a deprecated alias, and Vercel has renamed "evaluation models" to "decision models" across a small category that now includes Perplexity, Microsoft, Liquid and OpenAI entrants ([Vercel Decision docs](https://vercel.com/docs/ai-gateway/modalities/decision)). The Gateway shape is the vendor-neutral one: target it and you inherit Gateway's "decision fallbacks", which rerun a question on another model when, say, confidence falls below 0.6, at the cost of paying for and waiting on both stages.

"Type-safe" here means something narrower than it does in Hashbrown. The `@typesafe-ai/sdk` package offers builders (`choice`, `noul`, `score`, `box`) whose answer types are inferred, and its exported `ResultFor<T>` conditional type preserves criteria keys, so a choice answer comes back typed as the literal union of its option names ([TypeSafe JS SDK](https://docs.typesafe.ai/sdk/javascript.md); [ResultFor](https://docs.typesafe.ai/sdk/javascript/api/type-aliases/ResultFor.md)). The AI SDK does the same: `result.answers.department.choice` is typed `'billing' | 'support'` ([AI SDK Decisions](https://ai-sdk.dev/docs/ai-sdk-core/evaluation)). There is no Zod, no Standard Schema, and no schema for the state. The type safety is that the answer always matches the question's shape; TypeSafe's "zero hallucinations" marketing means exactly that schema guarantee, not a zero error rate ([StartupHub](https://www.startuphub.ai/news/typesafe-jev-model-kills-chat)).

### Runtime, access and cost favour a server route

Every documented example runs server-side with a secret key on Node 20 or 22+ (the SDK overview and quickstart disagree on the minimum), and nothing documents CORS on `api.typesafe.ai` ([JS SDK](https://docs.typesafe.ai/sdk/javascript.md); [Quickstart](https://docs.typesafe.ai/introduction/quickstart.md)). Calls **do not stream**: `experimental_decide` returns once, with `maxRetries` defaulting to 2 ([AI SDK Decisions](https://ai-sdk.dev/docs/ai-sdk-core/evaluation)). Requests cap at **64k tokens total and 32k per question**, raised to 262k with a long-context flag that TypeSafe itself calls slower and less accurate ([AI SDK TypeSafe provider](https://ai-sdk.dev/providers/ai-sdk-providers/typesafe-ai)). Questions in one call run "in parallel and in isolation against the same state", and adding questions "barely changes response time" ([TypeSafe intro](https://docs.typesafe.ai/introduction)), which makes fan-out (many small questions in one request) the idiomatic shape. Model IDs are `jev-1.13.0`, `jev-1.14.0`, `jev-latest` and `jev-preview`; Promptfoo warns that the `jev-latest` alias can shift scores without a config change, so pin versions ([Promptfoo](https://www.promptfoo.dev/docs/providers/typesafe/)). Direct keys came through a waitlist at launch; the Gateway path needs only a Gateway key with the `typesafe-ai` provider enabled for the team ([azukiazusa](https://azukiazusa.dev/en/blog/json-render-jev)). Enterprise accounts get zero data retention; non-enterprise retention is unspecified.

The speed claims are vendor-only and inconsistent. TypeSafe claims **70 to 500 ms end to end**, measured "from West Coast laptops", against reference answers that were averages of two frontier LLMs, with no independent evals at launch, and the headline multipliers vary between sources (193.6x faster and 444.6x cheaper on one page, 133x on another) ([StartupHub](https://www.startuphub.ai/news/typesafe-jev-model-kills-chat)). Numeric rate limits are not published. Treat the latency as plausible but unproven for atc's vocabulary until a prototype measures it.

### The documented weaknesses land squarely on ADS-B data

TypeSafe publishes an unusually frank list of Jev 1.13's rough edges: literal reading, **counting**, **arithmetic and numeric encodings including hex**, weakly calibrated score levels, **dates treated as text**, indirection and double negatives, accuracy loss with long or irrelevant context, adversarial or injected state, contradictory criteria, a **bias toward the first-listed choice option**, and no text generation or multi-step reasoning ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)). Choice probabilities are relative to the listed labels, so a catch-all `other` option is needed to avoid confident wrong answers, and Jev returns no rationale ([Promptfoo](https://www.promptfoo.dev/docs/providers/typesafe/)). For atc this is decisive. Raw altitudes, ground speeds, distances, timestamps and ICAO hex codes are exactly the inputs Jev handles worst. Any atc integration must compute in code and hand Jev named buckets such as "climbing", "below 10,000 ft" or "within 5 nm", and must never ask it to pick a plane by hex.

The Workday story deserves a caveat. The New Stack's headline "Workday is using TypeSafe's Jev to build user interfaces on the fly" (2026-10-13) was confirmed, but the article body could not be retrieved, so details circulating in search snippets (Workday handing Jev every atomic design-system component, a dashboard falling from 29 s to 3.8 s) remain unverified ([The New Stack](https://thenewstack.io/workday-is-using-typesafes-jev-to-build-user-interfaces-on-the-fly/)). A claimed CopilotKit recipe in which Jev picks a prebuilt panel was not found at all.

## json-render's Jev mode makes the model a picker and placer

The one concrete generative-UI integration is json-render's, added in **0.21.0** as `experimental_composeSpec` and `experimental_createEvaluator` "to compose validated specs from app-owned candidates" ([json-render CHANGELOG](https://github.com/vercel-labs/json-render/blob/main/CHANGELOG.md)). The json-render docs say the API is "not yet published to npm" and advise pinning exact versions ([json-render docs](https://json-render.dev/docs/jev)). The app defines a Zod catalog with `defineCatalog`, then supplies **candidates**: objects with an `id`, a natural-language `description`, an optional `root` flag, an optional `maxUses`, and an `element` whose `type` and `props` are already filled in by app code, including state bindings such as `{ $bindState: '/name' }` ([azukiazusa](https://azukiazusa.dev/blog/json-render-jev.md)). Jev then answers two batched rounds of questions. A `select` evaluation decides which candidates (and which root) to use; a `layout` evaluation decides each one's parent and position. The default "batch" strategy keeps the request count flat as element count grows; a "sequential" strategy evaluates element by element. The raw questions are not shown anywhere, but the limits suggest one noul per candidate for selection and one choice over parent-slot pairs per candidate for layout.

The output is an async iterator of `step` events, each carrying a **full spec snapshot** rather than json-render's usual SpecStream patches, and a terminal event with a `stopReason` of `finish`, `unavailable` or `limit`. Defaults cap the run at 32 evaluations, 32 elements and depth 8, and v1 supports only literals, `$state`, `$bindState` and visibility: no repeats, computed values or templates ([json-render docs](https://json-render.dev/docs/jev)). Transport is Gateway's "experimental v4 evaluation endpoint" with model ID `typesafe-ai/jev`, React is the only framework mentioned, and the docs state the design principle plainly: Jev "can only choose from the candidates you supply" and "doesn't invent missing copy or data" ([json-render docs](https://json-render.dev/docs/jev)). The only public walkthrough tested one prompt and one UI and measured no latency ([azukiazusa EN](https://azukiazusa.dev/en/blog/json-render-jev)).

The lesson for Hashbrown is that this pattern moves prop authoring back into application code. That suits forms and dashboards assembled from known panels, but it is the opposite of what Hashbrown is built to showcase, where the LLM writes typed props as a stream and fallbacks render partial values. Copying json-render's composer wholesale would make Hashbrown a second, Angular-capable json-render. Taking the smaller idea, typed decisions over a developer-owned set, fits Hashbrown's grain.

## Neighbouring specs split into three tiers, and Hashbrown already owns two seams

Hashbrown's own UI wire format is a **nested tree keyed by tag name**: a UI kit makes the model emit `{"ui":[{"FlightCard":{"props":{...},"children":...}}]}`, built in Skillet as an `anyOf` of single-key objects and sent to OpenAI as a strict `json_schema` response format (`packages/core/src/ui/ui-kit.ts:95-110`; `packages/openai/src/stream/text.fn.ts:113-129`). On the client each `props` is wrapped by `s.node` into `{ complete, partialValue, value }`, so a fallback renders partial props and the real component renders only once props validate (`packages/core/src/schema/base.ts:1610-1708`). That "typed while streaming" property, plus hold-back of non-streaming props like atc's `hex`, is the thing no neighbour replicates exactly.

| Spec | What it is | Type story | Streaming | Closeness to Hashbrown | What "support" would mean |
|---|---|---|---|---|---|
| TypeSafe Jev | Decision model; picks among typed options | Inferred answer types (literal unions) | No | Conceptual: controlled choices | Skillet-to-questions bridge; decision hook/resource |
| json-render (Vercel) | Flat id-keyed spec from a Zod catalog | "Type-safe component registry" | SpecStream patches | Highest: catalog plus validated props | Spec-to-tree translator; catalog export; fills its Angular gap |
| A2UI (Google) | JSONL surface/component/data-model messages | Catalog validation; no TS codegen found | Yes | High; has data bindings Hashbrown lacks | Translator plus catalog export, carried over AG-UI |
| MCP Apps (SEP-1865) | HTML in sandboxed iframes via `ui://` resources | None at UI level | N/A | Low; different trust model | Iframe host component |
| OpenUI (Thesys) | Line-oriented OpenUI Lang, not JSON | Zod component libraries | Yes | Competes with Skillet streaming | Second parser; low value |
| AG-UI | Transport, "not a generative UI specification" | Event types | Yes | Already Hashbrown's wire | Handle ACTIVITY events |
| Standard Schema | Cross-library schema interface | `~standard` validate plus JSON Schema | N/A | Already ingested | Have Skillet emit `~standard` too |

**json-render** is the closest relative: a Zod catalog where "if a component or prop is not in the catalog, AI cannot generate it", a flat `{ root, elements: { id: { type, props, children } }, state }` spec with `$state`, `$cond`, `$template` and `$computed` expressions, and renderers for React, Vue, Svelte, Solid, React Native and more, but **no Angular package** ([GitHub](https://github.com/vercel-labs/json-render); [skills.sh](https://www.skills.sh/yonatangross/orchestkit/json-render-catalog)). It launched in January 2026 and passed 200 releases by March ([InfoQ](https://infoq.com/news/2026/03/vercel-json-render)). LangChain's docs list Angular among its renderers, which conflicts with the README ([LangChain](https://docs.langchain.com/oss/python/langchain/frontend/declarative-generative-ui)); the README is the safer source.

**A2UI** is Google's Apache-2.0 format, now at **v0.9.1 with v1.0 a candidate**, using the MIME type `application/a2ui+json` ([a2ui.org](https://a2ui.org/)). Version 0.9 messages carry exactly one of `createSurface`, `updateComponents` (a flat component list with a `root` id), `updateDataModel` (JSON Pointer plus value) or `deleteSurface`, and children are id arrays or data-bound templates ([A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/)). The v0.9 announcement added an SDK that repairs partial streamed JSON, runtime-switchable catalogs, and official renderers for Flutter, Lit, Angular and React ([Google Developers Blog](https://developers.googleblog.com/a2ui-v0-9-generative-ui/)); a2ui.org's own renderer list omits React, so that point is unsettled. A2UI already has an official Angular renderer, so Hashbrown's edge there would be the typed catalog and its streaming semantics rather than framework coverage.

**MCP Apps** became the first official MCP extension: tools reference `ui://` HTML resources served as `text/html;profile=mcp-app`, hosts render them in sandboxed iframes and bridge JSON-RPC over `postMessage`, and servers must still return a text result ([MCP SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp); [MCP blog](https://blog.modelcontextprotocol.io/posts/2025-11-21-mcp-apps/)). That conflicts with Hashbrown's "never sends HTML or code" positioning and with atc's trusted-rendering invariant. **OpenUI** from Thesys emits a compact line-oriented language instead of JSON, ships its own Angular runtime, and claims up to 67% fewer tokens than JSON, which an independent check put at about 2.1x ([GitHub](https://github.com/thesysdev/openui); [mer.vin](https://mer.vin/2026/05/openui-lang-mit-generative-ui-that-cuts-llm-output-tokens-versus-json/)); supporting it means a second parser that competes with Skillet. **AG-UI** describes itself as "not a generative UI specification" but the runtime connection that carries A2UI, Open-JSON-UI and MCP-UI, with `ACTIVITY_SNAPSHOT` and `ACTIVITY_DELTA` events (RFC 6902 patches) for exactly this kind of payload ([AG-UI generative UI specs](https://docs.ag-ui.com/concepts/generative-ui-specs); [AG-UI events](https://docs.ag-ui.com/concepts/events)). CopilotKit's taxonomy of static, declarative and open-ended generative UI maps these neatly: Hashbrown is static-plus-declarative, A2UI and json-render are declarative, MCP Apps is open-ended ([CopilotKit](https://www.copilotkit.ai/blog/the-developer-s-guide-to-generative-ui-in-2026)).

**Standard Schema** is the cheapest type-safety interop. `StandardJSONSchemaV1` adds a `~standard.jsonSchema.input/output({ target })` converter that Zod already satisfies ([JSR @standard-schema/spec](https://jsr.io/@standard-schema/spec/doc/~/StandardJSONSchemaV1)). Hashbrown already **ingests** it: core vendors the interface, `s.fromStandardJsonSchema` converts to Skillet, and component props, tools and outputs accept Zod or ArkType (`packages/core/src/schema/standard-json-schema.ts`). The remaining direction, Skillet schemas implementing `~standard` so they plug into the AI SDK, TanStack AI and others, is unverified as to effort but small in scope.

Hashbrown already has two outward seams that matter here. **`createUiJsonSchema`** exports a kit as plain JSON Schema identical to what `useUiChat` sends, and the CopilotKit recipe uses it to drive a foreign agent (`packages/core/src/ui/ui-json-schema.ts`; `www/content/docs/react/recipes/copilotkit.md`). And core speaks AG-UI 1.0 natively. The gap is that the message reducer **silently drops ACTIVITY events** (`packages/core/src/reducers/ag-ui-messages.reducer.ts:325-327`). Surfacing them on the view model, the way `serverToolCalls` surfaced unknown server tools, is the prerequisite for any foreign-spec renderer.

## A Skillet-to-Jev bridge is the right API shape

Hashbrown should model Jev as **typed decisions, not typed UI**. Skillet already has every primitive a bridge needs: `s.enumeration` takes a const tuple and infers a literal union, `s.boolean` exists, and `s.number` carries `minimum`, `maximum` and `multipleOf` constraints (`packages/core/src/schema/base.ts`). A pure compiler can turn a top-level Skillet object into one fan-out Jev request, one question per property, with the property key as the question ID, which matches Jev's parallel-and-isolated evaluation model exactly.

| Skillet | Jev question | Rule |
|---|---|---|
| `s.enumeration(desc, [...])` or `s.anyOf` of literals | `choice`, `instructions: desc`, one criterion per entry | Up to 255 entries; recommend an `other` entry; same literal union as Jev's own SDK infers |
| `s.boolean(desc)` | `noul` (native) / `boolean` (Gateway) | Expose the probability; threshold in code, default 0.5 |
| `s.number` with bounds giving 2 to 10 steps | `score` with generated levels | Map the expected score back to range; coarse ratings only, since levels are weakly calibrated |
| nested `s.object` | flattened dotted question IDs | Still one request |
| `s.string`, `s.array`, `s.streaming.*`, unbounded numbers | rejected at compile time | Jev cannot generate text or counts |

The result envelope should be `{ value, meta }`, where `value` is the inferred Skillet type and `meta` holds each field's probability, probabilities and confidence, so applications can follow TypeSafe's documented confidence-routing pattern ([TypeSafe docs index](https://docs.typesafe.ai/llms.txt)). A useful Skillet addition is optional per-entry descriptions on enumerations, because Jev uses criterion descriptions to discriminate options.

Layered on that, the recommended package shape (an inference from the repo's conventions, not a sourced design) has four parts. First, a pure, network-free core compiler and decoder, `ɵskilletToDecisionQuestions` plus a decode step, exported with the `ɵ` prefix as AGENTS.md requires for cross-package internals. Second, a server adapter, `@hashbrownai/typesafe`, whose `decide({ apiKey, baseURL, model, state, schema })` returns `{ value, meta }`; `baseURL` switches between `api.typesafe.ai` and Gateway's `/typesafe`, and a raw `fetch` avoids adding `@typesafe-ai/sdk` as a dependency, which AGENTS.md says needs maintainer approval. Optionally it can also emit AG-UI `RUN_STARTED`, a single `STATE_SNAPSHOT` or tool result, and `RUN_FINISHED`, so the existing transport carries it unchanged. Third, framework APIs as non-streaming siblings of what already exists: React `useDecision({ schema, state, debounceMs })` returning `{ value, meta, isLoading, error }`, and Angular `decisionResource({ schema, state: computed(...) })` modelled on Angular's `resource()`. Their public types must expose only non-`ɵ` types. Fourth, and later, a json-render-style `useUiDecision({ components, candidates })` that turns registered components into a choice while app code pre-fills props.

The alternative, targeting AI SDK `experimental_decide` instead of Jev's own wire, buys Gateway fallbacks and other decision models for free but ties Hashbrown to an experimental API that has already been renamed once. The bridge design keeps that option open: the compiler produces a neutral question map, and the adapter is a thin wire mapping.

## In atc, Jev should route the filter before the assistant streams

atc teaches "expose your components, give the model tools, render the stream", in Angular and React from shared, framework-free Skillet contracts (`examples/atc/README.md:3-8`, `43-64`). The planned natural-language map filter is already well served by Hashbrown's existing `useStructuredCompletion` and `structuredCompletionResource`, and atc's existing `findAircraftInput` schema in `examples/atc/shared/src/tool-definitions.ts` could serve unchanged as the structured-completion schema: one Skillet schema used as tool arguments, structured output and server-pinned JSON Schema. Jev's best role is in front of that, not instead of it.

The headline demo is a **router plus instant filter**. On submit, the atc server makes one Jev call with five fan-out questions over compact state (the user's text, the visible airports, code-computed summaries): `intent` as a choice of filter, chat, map command or other; `preset` as a choice of arrivals, departures, low-and-slow, helicopters, military, airlines, general aviation or none; `airport` as a choice over the region's ICAO codes plus none; `altitudeBand` as a choice of surface, below 10k, above 10k or any; and `clearsFilter` as a noul. A confident filter applies to the map in about the time of a network round trip, with no tokens streamed. Low confidence, or `intent = chat`, falls through to the current streaming assistant, which can still call `findAircraft`. This showcases the "System One in front of System Two" pattern that TypeSafe documents as intent routing and confidence routing ([TypeSafe docs index](https://docs.typesafe.ai/llms.txt)), it needs no prop authoring by Jev, and its Skillet declaration is the same few lines of `s.enumeration` and `s.boolean` an atc developer would write for structured completion. The planned **"Show the stream"** view makes the contrast legible: on the Jev path it shows a single decision snapshot with per-field probabilities and the elapsed milliseconds; on the LLM path it shows AG-UI events and each `s.node`'s `complete` and `partialValue` filling in. Side by side, that is the clearest explanation yet of when to stream and when to decide.

Three secondary demos are weaker. **Card choice for a selected plane** (ask `view` as a choice of FlightCard, ArrivalsBoard, AircraftCompare or AirportCard, with props such as `hex` filled by app code) mirrors json-render's candidate pattern and could replace a hand-written system-prompt rule in `examples/atc/shared/src/contracts.ts`, but that rule is nearly deterministic, so the demo proves little. A **"what's notable" panel** that asks noul or score questions over code-computed buckets per aircraft, weighted in code, follows the composite-scoring pattern but must batch 50 to 200 visible aircraft and watch context length. **Guardrails before map moves** have the least demo value.

The atc invariants shape the implementation. The call belongs in `atc-server`, because CORS and key exposure are undocumented. Inputs must be buckets, never raw numbers or hex. Option order should be randomized or consistency-checked against the first-option bias. And `jev-1.14.0` or whichever version is tested should be pinned rather than `jev-latest`.

### Effort and risk, honestly estimated

These estimates are judgements from the codebase inspection, not sourced figures.

| Work item | Effort | Main risk |
|---|---|---|
| Core `ɵ` Skillet-to-question compiler and decoder, with tests | S | Score mapping semantics; per-entry descriptions need a small Skillet addition |
| `@hashbrownai/typesafe` adapter over raw `fetch` (native and Gateway) | S-M | Two wire dialects (`noul` vs `boolean`, snake vs camel case); unpublished rate limits |
| React `useDecision` and Angular `decisionResource` | M | New public API surface for a vendor that is weeks old |
| atc router plus instant filter, with an e2e path | M | Accuracy on airport and type vocabulary is untested; needs a live key in CI or recorded fixtures |
| "Show the stream" decision panel | S, given the planned view | None notable |
| json-render-style candidate composer | M-L | Duplicates json-render; weak fit with Hashbrown's streaming story |

The strategic risks outweigh the engineering ones. TypeSafe launched in early access on a waitlist a month ago, the json-render mode is experimental and unpublished, the AI SDK name has already changed, and every performance number is self-reported. Shipping a core-level dependency on that would be premature. The `ɵ` compiler plus a separately versioned adapter package contains the blast radius: if Jev fades, the compiler still targets any decision model behind Gateway or `experimental_decide`.

For the wider interop track, the inspection suggests a different order from the Jev work. First, have the atc server build the UI schema with `createUiJsonSchema` instead of trusting the client's, which today it must do because the Markdown component's definition lives inside the framework packages (`examples/atc/server/src/run-handler.ts:225-232`); exporting a framework-free Markdown definition from core closes that trust gap. Second, surface AG-UI ACTIVITY events in core (S-M). Third, an A2UI translator and catalog export, demonstrated by a server-side atc agent emitting A2UI that renders through atc's own Angular and React components (M-L, with the spec still moving toward v1.0). json-render support is optional and mainly valuable as "json-render specs in Angular". MCP Apps and OpenUI belong on the explicit non-goals list.

## Conclusion

Jev reframes the generative UI question. The neighbouring specs all compete on how a model *describes* an interface; Jev skips description and asks the model only to *decide*, trading expressiveness for an order-of-magnitude cut in latency and cost on the narrow class of choices it handles well. Hashbrown's natural move is not to adopt Jev's UI composer but to recognise that a Skillet enumeration is already a typed decision, and to let developers send that same schema to a decision model when they do not need prose or streamed props. That makes "type-safe" mean one thing across both paths: the schema the developer writes determines the result type, whether the answer arrives as a stream of validated props or as a single probability-weighted choice.

The atc router is the right proving ground precisely because it exposes Jev's limits. Map filtering demands that Jev never see a raw altitude or hex code, that low-confidence answers fall back to the streaming assistant, and that the stream view shows users which path answered. If Jev's claimed sub-second latency holds on real aviation vocabulary, atc gains a filter that feels instant and a teaching moment about when to decide versus when to generate. If it does not, the bridge still stands, pointed at whichever decision model the Gateway routes to next.
