# B4 findings from dog-fooding the invoicing example

Drafts, one per finding in the design spec's "Upstream findings" section, ready
to file against `cacheplane/b4run` (B4 0.8.36). Nothing here has been filed.
File paths are relative to `examples/invoicing/` in this repository.

---

## 1. `createAgentHarness` runs no route middleware

**Title:** `createAgentHarness`: add a `middlewareContext` option so tools that depend on route middleware can be evaluated

`@b4run/testing`'s `createAgentHarness` invokes a route's agent directly, so
`middleware.ts` never runs and a tool that reads its context (a session, a
database handle, a per-request snapshot) sees `undefined`. Any app whose tools
depend on middleware cannot use `b4 eval` at all: every case fails on the
first tool call, and there is no option to supply the context the middleware
would have produced. `streamResolvedRoute` already accepts a
`middlewareContext`, so the harness is the only missing seam.

The invoicing example's assistant tools read the visitor's ledger snapshot and
session from the middleware context (`server/src/assistant-middleware.ts`,
consumed by `server/src/assistant-tools.ts`). To run its evals the example
ships its own harness, `server/evals/harness.ts`, which boots the whole server
in-process against an aimock instance, opens a session cookie via
`GET /api/snapshot`, and posts each case's AG-UI request to the real
`/agui/%2Fassistant%23agent` route; `server/evals/run.ts` hands the collected
stream to `runEval` as the `runCase` callback. That harness exists only
because of this gap and would be deleted once `createAgentHarness` accepts a
`middlewareContext` (or a function producing one per run).

**Minimal reproduction**

1. In `examples/invoicing/server`, replace the `runCase` in `evals/run.ts`
   with `createAgentHarness({ appRoot, route: '/assistant' })` and call
   `harness.run({ input: 'How does Summit Logistics usually pay?' })`.
2. Observed: the first tool call (`ledgerSummary`) throws `invalid_context`
   from `assistantTools()` in `server/src/assistant-tools.ts`, because
   `context.middleware` is undefined; the case fails with a tool error.
3. Expected: a way to pass the context `middleware.ts` would have produced,
   e.g. `createAgentHarness({ ..., middlewareContext })`, threaded to
   `streamResolvedRoute`.

## 2. Client `responseSchema` is accepted and ignored

**Title:** `hashbrown.responseSchema` in the AG-UI body is neither applied to the root model nor rejected

Hashbrown's client sends `hashbrown: { ui: true, responseSchema }` on every
run so the model's final message conforms to the UI schema. B4 accepts the
field and reads nothing from it: the root model runs with no
`response_format`, and the only way an app can honour the schema is a tool
that calls `withStructuredOutput` itself. The schema is silently a no-op,
which is the worst of both options: the client believes the contract is
enforced, and the app finds out only when a closing message fails to parse.
`tools` sent by the client are rejected (#740); `responseSchema` should get
the same treatment, or be applied as the root model's response format.

The invoicing example's assistant prompt ends with "After render, output
exactly `{"ui":[]}`" precisely because nothing enforces the schema. The
recorded eval tapes show the cost: in one nine-case record run against
`gpt-5-mini`, four cases closed with `{}` instead of `{"ui":[]}`, and the
schema the client sent (`shared/src/assistant-contract.ts`,
`assistantResponseSchema`) has `required: ["ui"]`. The client survives it
only by accident: `@hashbrownai/core` keeps a message whose content misses
the response schema without resolving it, so nothing renders and no error is
raised, whereas a prose closing message surfaces the app's error alert. The
example's eval therefore accepts any silent JSON closing rather than the
exact string. The server reads `body.hashbrown.responseSchema` only to hand
it to the nested `render` tool (`server/src/assistant-middleware.ts:59`).

**Minimal reproduction**

1. `npx nx run invoicing-server:eval` (replay, no key).
2. Observed: `cedar open invoices`, `eur trend`, `atlas match` and
   `habit summit` fail `endsWithEmptyUi`; the last app fixture in each of
   `server/src/app/assistant/evals/assistant.cedar-open-invoices.fixtures.json`,
   `assistant.eur-trend.fixtures.json`, `assistant.atlas-match.fixtures.json`
   and `assistant.habit-summit.fixtures.json` has `"content": "{}"`, although
   every request carried `hashbrown.responseSchema` with `ui` required.
3. Expected: either the run is rejected because `responseSchema` is not
   supported, or the root model is invoked with that schema as a strict
   `response_format`, which makes `{}` impossible.

## 3. Tool schema derivation ignores the app's `tsconfig` paths

**Title:** Schema compiler resolves path-aliased imports to `any`, derives `{ properties: {} }`, and `b4 typegen` reports success

B4 derives each tool's input schema from its TypeScript input type by building
its own TypeScript program. That program does not read the app's `tsconfig`
`paths`, so an input type imported through an alias resolves to `any`, the
derived schema is an empty object, and the model is told the tool takes no
arguments. `b4 typegen` prints success, so the first sign is a tool that is
called with `{}` at runtime. Two fixes, both worth doing: build the program
from the app's tsconfig (or accept a `tsconfig` option), and fail loudly when
an input type resolves to `any` or the derived schema has no properties.

The invoicing example hit this on its `render` tool, whose input type
`AssistantRenderInput` lives in the `@invoicing/contracts` workspace package.
`server/src/app/assistant/tools/render.ts` (lines 3-8) now imports it by a
relative path (`../../../../../shared/src/assistant-ui`) with a comment
pointing at this finding, and
`server/src/assistant-tool-schemas.spec.ts` derives the route's schemas the
way `b4 typegen` does (`extractToolSchemasForRoute`) and pins the `render`
schema's properties, as a regression guard.

**Minimal reproduction**

1. In `examples/invoicing/server/src/app/assistant/tools/render.ts`, change
   the `AssistantRenderInput` import back to
   `import type { AssistantRenderInput } from '@invoicing/contracts';`
   (the alias is declared in `server/tsconfig.json`).
2. Run `npx b4 typegen` in `examples/invoicing/server`, then
   `npx nx test invoicing-server -- assistant-tool-schemas`.
3. Observed: typegen succeeds; the derived schema for `render` is
   `{ "type": "object", "properties": {} }` and the spec fails.
4. Expected: the schema derived from `AssistantRenderInput` (`text` plus
   `components`), or a typegen error naming the unresolved import.

## 4. A thrown tool error never reaches the AG-UI stream

**Title:** LangChain adapter emits no `TOOL_CALL_RESULT` when a tool throws

The `@b4run/langchain` adapter maps `on_tool_end` to a `tool_result` chunk
and emits nothing on `on_tool_error`. A client therefore sees
`TOOL_CALL_START`, `TOOL_CALL_ARGS` and `TOOL_CALL_END` for a failing tool
and never a `TOOL_CALL_RESULT`; the error `ToolMessage` that LangGraph hands
the model appears only inside `RUN_FINISHED.result.messages`. From the
stream alone a tool that threw is indistinguishable from one still running,
and any client that renders tool results (or any eval scorer that counts
tool errors) has to dig through the final message list instead.

The invoicing eval harness does exactly that. `server/evals/collect-run.ts`
handles `RUN_FINISHED` by walking `result.messages`, picking every
`ToolMessage` whose `tool_call_id` has no result yet, and backfilling an
`isError` tool result from it (see the comment at the `RUN_FINISHED` case).
The `noToolErrors` scorer in `server/src/app/assistant/evals/assistant.eval.ts`
depends on that backfill. Emitting a `TOOL_CALL_RESULT` carrying the error
`ToolMessage` (with the same `tool_call_id`) would let the backfill go.

**Minimal reproduction**

1. Through the invoicing harness (`server/evals/harness.ts`), ask the
   assistant a question that makes a query tool throw, e.g. a
   `customerStatement` call with a customer ID that does not exist (the
   model can do this when a name is misspelled), or temporarily make
   `server/src/app/assistant/tools/aging.ts` throw.
2. Observed on the wire: `TOOL_CALL_START`, `TOOL_CALL_ARGS`,
   `TOOL_CALL_END` for that call, no `TOOL_CALL_RESULT`; the error text is
   present only in `RUN_FINISHED.result.messages` as a `ToolMessage` with
   `status: "error"`.
3. Expected: a `TOOL_CALL_RESULT` event for the failing call carrying the
   error content, so `run.toolResults` in `@b4run/testing` marks it
   `isError` without reading `RUN_FINISHED`.

## 5. No post-run hook on the final assistant message

**Title:** Provide a server-side seam (`middleware.after` or an output guard) to validate or rewrite the final assistant message

The only place an app can validate model output on the server is inside a
tool. A read path that wants to check composed UI against a kit and a
session snapshot, before anything reaches the client, has to route the
model's answer through a tool that does the validation and then ask the
model to emit a fixed closing message. That detour costs an extra model turn,
makes the closing message a prompt-level contract (finding 2 shows how
fragile that is), and hides the validation in a tool the model could skip.

The invoicing example's `render` tool exists for this reason:
`server/src/app/assistant/tools/render.ts` receives prose and component
nodes, `server/src/assistant-ui.ts` (`validateUi`) rejects unknown
components and IDs not in the session's snapshot, and only then is the UI
sent to the client, after which the prompt demands `{"ui":[]}` as the final
message. A `middleware.after(run)` hook, or an output guard given the final
message and the middleware context, would let the same validation run on the
model's actual final message with no tool detour and no closing-message
convention.

**Minimal reproduction**

1. Read `server/src/app/assistant/index.ts`: the system prompt instructs the
   model to call `render` exactly once as its last action and then output
   exactly `{"ui":[]}`.
2. Try to move the validation in `server/src/assistant-ui.ts` out of the
   `render` tool and onto the final assistant message: there is no hook in
   `@b4run/sdk`'s `agent()` options or in `middleware.ts` that runs after
   the model's last message with access to the middleware context.
3. Expected: an `after` hook (or output guard) receiving the final message
   and the middleware context, able to reject or replace it before the
   `RUN_FINISHED` event.
