Today we are releasing Hashbrown v0.8.

The headline is decisions.
Hashbrown has always talked to generative models.
Now it also talks to decision models.
The first one is [TypeSafe](https://docs.typesafe.ai)'s Jev.

There are breaking changes in this release, and I want to be upfront about them.
UI kits no longer take few-shot examples, the `prompt` tagged template is gone, the OpenAI and Azure adapters moved to the Responses API, and the run-input extension moved to where AG-UI 1.0 wants it.
Let's break each of these down.

**Release at a glance**

- `useDecision()` and `decisionResource()`: a typed answer, with confidence, from a decision model.
- `useUiDecision()` and `uiDecisionResource()`: let a decision narrow your chat to the components that fit each message.
- `@hashbrownai/typesafe`: a server-only adapter for TypeSafe's Jev.
- `decodeDecision()` and `createSelectionSchema()`, so an agent can decide on the server and pin the questions.
- `AgentRunError`: a server's run error reaches `error` with its code.
- UI kits: rules in descriptions replace few-shot examples, and `prompt` is removed.
- `setComponents()` now changes what the model may render, and earlier answers keep rendering when you remove a component.
- `markdownComponent()`, so a server can pin the full UI response schema.
- OpenAI and Azure stream from the Responses API, with reasoning summaries on by default for reasoning models.
- The run-input extension moves into `forwardedProps.hashbrown`.
- `lastRunResult`: the run's return value, on every chat and completion API.
- A cancelled run settles cleanly instead of raising an error.
- AG-UI activities: plans, progress and background work reach `chat.messages`, every provider can send them, and `groupTurns()` groups a turn.
- User and assistant messages carry a stable `id`.
- A v0.8 migration guide for React and Angular, with a prompt for your AI coding assistant.

## Decisions

### What?

A decision is a closed question about your app state.

- Which panel should this query open?
- Is this message a complaint?
- On a scale of minus two to two, how urgent is this?

Each one has an answer from a set you define: an enumeration, a yes or no, or a number on a short scale.
A decision model answers the question directly, as a typed value with a probability attached.
It does not stream.
It does not write text.
It answers in about a hundred milliseconds, which is fast enough to run on every keystroke.

### Why?

Let's be honest about what we were doing before.

We were asking a generative model to answer closed questions with structured output.
It works.
It is also slow, it costs more than it should, and the answer comes back without a confidence.
When the model is wrong, you find out from the user.

A decision model is built for this.
You get the answer, you get the probability of every option, and you can route on both: act when the model is sure, and fall back to generation when it isn't.

Here is how I think about the split:

| Task                                    | Use        |
| --------------------------------------- | ---------- |
| Route a question to the right panel     | Decision   |
| Pick which card to show for a query     | Decision   |
| Classify, triage or tag input           | Decision   |
| Write an answer, summary or explanation | Generation |
| Fill in the props of a component        | Generation |

### How?

You ask with a Skillet schema.
`s.enumeration()` gains per-option descriptions in this release, so the model knows what each option means:

<hb-code-example header="route a question">

```tsx
import { s } from '@hashbrownai/core';
import { useDecision } from '@hashbrownai/react';

const routeSchema = s.object('Where to send the question', {
  intent: s.enumeration('What the user wants to do', {
    filter: 'Narrow the list of flights on the map',
    chat: 'Ask a question that needs a written answer',
    other: 'Anything else',
  }),
  clear: s.boolean('The user wants to clear the current filter'),
});

function Search({ query }: { query: string }) {
  const route = useDecision({
    schema: routeSchema,
    input: query === '' ? null : query,
    system: 'You route questions in a flight-tracking app.',
    debounceTime: 150,
  });

  if (route.value?.intent === 'filter') {
    return <FilterPanel />;
  }

  return <Chat />;
}
```

</hb-code-example>

Let's break that down:

1. `routeSchema` is a `DecidableSchema`. TypeScript checks it at compile time, so it can only ask what a decision model can answer: enumerations, booleans, bounded numbers and objects of those.
2. `input` is the thing to decide about. Pass `null` when there is nothing to ask yet.
3. `value` is typed from the schema.
4. `meta` mirrors the shape of `value` and carries the model's confidence for each question.

In Angular, `decisionResource()` takes the same schema and returns signals:

<hb-code-example header="search.component.ts">

```ts
readonly route = decisionResource({
  schema: routeSchema,
  input: computed(() => (this.query() === '' ? null : this.query())),
  system: 'You route questions in a flight-tracking app.',
  debounce: 150,
});
```

</hb-code-example>

### Decide which UI to show

This is the part I am most excited about.

`useUiDecision()` and `uiDecisionResource()` let a decision pick components.
There are two modes:

1. **Candidates.** Your code builds every option, and the model picks which ones to show. The model never writes a prop.
2. **Chat.** You keep your own chat, with its own system prompt, tools and transcript. A decision picks from the chat's components, the chat is narrowed to the chosen ones, and the message is sent.

Here is chat mode:

<hb-code-example header="narrow a chat">

```tsx
const chat = useUiChat({
  system: 'Answer questions about live flights. Use the cards to show results.',
  tools: [getFlights],
  components: [flightCard, airportCard],
});

const { sendMessage, isDeciding } = useUiDecision({
  chat,
  select: { max: 2 },
  minConfidence: 0.7,
  system: 'A flight-tracking app. The input is a chat message.',
});
```

</hb-code-example>

Let's break that down:

1. `chat` is your `useUiChat`. Its system prompt, tools and transcript are used unchanged, so a card can still be filled from a tool result.
2. `system` here is context for the decision model only: what the app is, and what the input means. Layout rules stay in the chat's own prompt, because they do not belong in a decision model's input.
3. `select` is the limit: `'one'`, or `{ max: 2 }`.
4. The decision looks inside kits. Every component is an option, and a chosen parent brings its declared children along.
5. Send through the hook. If the model is unsure, or the decision fails, the message goes out with every component. Nothing breaks; you get the behavior you had before. When the turn finishes, the chat's components are restored.

On the server, `createSelectionSchema()` from core produces exactly the questions the hook sends, so you can pin them the same way you pin a prompt.
The [UI Selection recipe](/docs/react/recipes/ui-selection) walks through both modes, kits, children, fallback and pinning.

### TypeSafe on the server

Decisions run on a server route that holds your key.
The default is `/api/decide`.

`@hashbrownai/typesafe` maps Hashbrown's decision protocol to Jev's API with `fetch`, so it adds no dependencies to your server:

<hb-code-example header="server.ts">

```ts
import { HashbrownTypeSafe } from '@hashbrownai/typesafe';

app.post('/api/decide', async (req, res) => {
  const decision = await HashbrownTypeSafe.decide({
    apiKey: process.env.TYPESAFE_API_KEY!,
    model: 'jev-1.14.0',
    request: req.body,
  });
  res.json(decision);
});
```

</hb-code-example>

A few things to know:

- It validates the client's request before any network call.
- It retries rate limits, and reports failures as a `DecisionError` with a typed code.
- Pass `schema` to pin the questions on the server, the same way you pin a prompt.
- Pin the model version. There is no `jev-latest`, and that is on purpose.

The protocol itself is plain JSON and vendor-neutral.
Jev is the first adapter, not the last.

Read [Decisions](/docs/react/concept/decisions) for the concept and the [TypeSafe platform page](/docs/react/platform/typesafe) for the server.

### Decisions inside your agent

Not every decision belongs in the browser.
An agent that runs in LangGraph, or in your own server, has the same closed questions: what should I do next, and is this urgent?

`decodeDecision()` is public in core for exactly this.
Call `HashbrownTypeSafe.decide` with a schema, then decode the response into a typed `value` and `meta`:

<hb-code-example header="next-step.ts">

```ts
import { decodeDecision, s } from '@hashbrownai/core';
import { HashbrownTypeSafe } from '@hashbrownai/typesafe';

const nextStepSchema = s.object('Next step for a support conversation', {
  step: s.enumeration('What the agent should do next', {
    refund: 'Start a refund for the order',
    lookup: 'Look up the order before answering',
    answer: 'Answer from what is already known',
    human: 'Hand the conversation to a person',
  }),
  urgent: s.boolean('The customer says the problem is urgent'),
});

export async function decideNextStep(conversation: string) {
  const response = await HashbrownTypeSafe.decide({
    apiKey: process.env.TYPESAFE_API_KEY!,
    model: 'jev-1.14.0',
    schema: nextStepSchema,
    request: { state: conversation },
  });
  const { value, meta } = decodeDecision(nextStepSchema, response);

  return meta.step.confidence >= 0.7 ? value : null;
}
```

</hb-code-example>

Return `null` when the model is not sure, and let the agent fall back to its language model.

The same recipe shows how to run decisions over AG-UI itself, in userland: the request travels in `forwardedProps.hashbrown.decision`, and the answer comes back in `RUN_FINISHED.result`.
That is the same field `lastRunResult` reads, which we will get to below.
And when a server does raise a run error, it now reaches `error` as an `AgentRunError` with a `code`, so your app can tell a rate limit from a bad request.

Read [Decisions in Agents](/docs/react/recipes/decisions-in-agents) for both recipes.

## UI Kits: Rules, Not Examples

This one is a removal, and I want to explain why.

Since the early days, Hashbrown had two ways to hand the model few-shot UI examples: `<ui>` blocks in the `prompt` tagged template, and an `examples` option on UI kits and the UI hooks.
I liked the idea.
In practice, it did not hold up:

1. OpenAI advises trying reasoning models without examples, and there is published research showing few-shot prompting degrading a reasoning model.
2. Strict structured output already guarantees the shape of the answer, which is most of what the examples were for.
3. A hand-written sample answer drifts. Change a prop, and the example is quietly wrong.
4. Examples were about to break narrowing in UI selection. An example that names a component the decision did not choose fails during render.

So in v0.8, `examples` and `prompt` are gone, with no compatibility shim.
Guidance now lives where it travels with the component:

1. **Component descriptions** say when to use the component, when not to, and how it differs from similar ones.
2. **Prop descriptions and schema constraints** hold value conventions: units, formats, ranges, allowed values.
3. **A short plain-string `system`** holds layout and composition rules.

Before:

<hb-code-example header="before">

```ts
useUiChat({
  system: prompt`
    You are a smart home assistant.

    <ui>
      <LightCard lightId="light-1" brightness={80} />
    </ui>
  `,
  components: [lightCard],
});
```

</hb-code-example>

After:

<hb-code-example header="after">

```ts
useUiChat({
  system: `
    You are a smart home assistant.

    - Show one LightCard for each light the user asks about.
    - Add at most one Markdown summary, after the cards.
  `,
  components: [
    exposeComponent(LightCard, {
      name: 'LightCard',
      description:
        'One light and its current state. Use it once per light the user asks about. For general explanations, use Markdown instead.',
      props: {
        lightId: s.string('The light ID from the getLights tool'),
        brightness: s.number('Brightness from 0 (off) to 100 (full)'),
      },
    }),
  ],
});
```

</hb-code-example>

A rule in a description changes when the component does, and leaves with it when the component is removed.
That is the property I want.

Two more kit changes ship alongside this:

- **`setComponents()` works the way you expected.** Before, `useStructuredChat` froze the schema at mount, so changing components on `useUiChat` or `useUiCompletion` changed the system prompt but not what the model could return. Removing a component also broke earlier answers that used it, and replacing a component under the same name kept the old one. All three are fixed: the schema follows the components, past answers render with every component the chat has offered, and the newest definition wins. Angular's `uiChatResource` gains `components` and `setComponents` to match.
- **`markdownComponent()` moves to core.** `createUiJsonSchema()` arrived in v0.7 so an agent you run yourself can build the schema your kit sends. The Markdown component's definition lived only in the React and Angular packages, so a server could not include it. Now it can, and the new [Securing a Public Endpoint](/docs/react/recipes/public-endpoint) recipe shows a server pinning the system prompt, the tools and the full UI schema, using [atc](https://github.com/liveloveapp/hashbrown/tree/main/examples/atc) as the worked example.

## OpenAI and Azure on the Responses API

The OpenAI and Azure adapters now stream from OpenAI's Responses API instead of Chat Completions.
Chat history, tools and structured output work as before.
What you gain is reasoning.

For a reasoning model, Hashbrown asks for reasoning summaries by default and streams them as AG-UI reasoning events, so your app can show the model thinking.
Each reasoning item's encrypted content comes back too, and Hashbrown replays it on the next turn from the client's own history.
Nothing is stored on OpenAI, so this works for zero-data-retention accounts.

<hb-code-example header="server.ts">

```ts
HashbrownOpenAI.stream.text({
  apiKey: process.env.OPENAI_API_KEY!,
  model: 'gpt-5',
  input,
  reasoning: { effort: 'low' },
});
```

</hb-code-example>

A few things to know:

1. Reasoning models are `o` plus a digit, `gpt-5` and up, except the `-chat` variants. Other models get no reasoning request.
2. Hashbrown never sends `effort` unless you set it. Set `reasoning: false` to stop requesting summaries.
3. `transformRequestOptions` now receives Responses params. `messages` become `input` items, and `max_completion_tokens` becomes `max_output_tokens`.
4. A server that only speaks Chat Completions, such as vLLM, OpenRouter or LM Studio in some modes, no longer works with `@hashbrownai/openai`. Keep that server on v0.7, or move to one that supports the Responses API.
5. Azure: pass the deployment as `model`, and use a Responses-capable `apiVersion`.

[atc](https://github.com/liveloveapp/hashbrown/tree/main/examples/atc) shows a reasoning row above each answer in both frameworks, if you want to see it in a real app.

## Activities

Some things the user should see and the model should not.
A plan.
A progress bar.
A background job that is still running.
AG-UI calls these activities, and in v0.8 Hashbrown supports them end to end.

On the client, `Chat.Message` gains a fourth variant, `role: 'activity'`, with an `id`, an `activityType`, untyped `content`, and `links` to the run, the assistant message and the tool call it belongs to.
Activities land in `chat.messages` where they arrived, and your app renders them:

<hb-code-example header="render a plan">

```tsx
case 'activity':
  return message.activityType === 'plan' ? (
    <ul key={message.id}>
      {planSteps(message.content).map((step) => (
        <li key={step}>{step}</li>
      ))}
    </ul>
  ) : null;
```

</hb-code-example>

When an activity belongs with the answer it describes, `groupTurns()` from core groups the flat list into turns and buckets each turn's activities by their links.

On the server, every provider takes an `activities` callback.
`activity.snapshot()` sends an activity and returns a handle you can `patch()` as the work moves along:

<hb-code-example header="server.ts">

```ts
HashbrownOpenAI.stream.text({
  apiKey: process.env.OPENAI_API_KEY!,
  model: 'gpt-5-nano',
  input,
  activities: async ({ activity, model }) => {
    const plan = activity.snapshot(`plan-${input.runId}`, 'plan', {
      steps: ['Read the question', 'Answer'],
      done: 0,
    });

    await model;

    plan.patch([{ op: 'replace', path: '/done', value: 2 }]);
  },
});
```

</hb-code-example>

The run waits for the callback to settle, so you can send activities before, during and after the model call.
The model never sees them, and Hashbrown never sends them back to the agent.

Two things come along with this:

1. User and assistant messages now expose a stable `id`, the canonical AG-UI message id. Activities link to it, and so does `groupTurns()`. If you save and restore a transcript, the ids and the links survive.
2. The provider packages now depend on `@hashbrownai/core`.

Read [Activities](/docs/react/concept/activities) for the flat and nested rendering patterns.

## What Do I Need to Change?

Let's start with the part you need to act on.
There are seven steps, and most apps need only the first.

### 1. Update packages together

Every `@hashbrownai/*` package in your app must be on the same version, and that now includes the server's adapter:

<hb-code-example header="terminal">

```sh
npm install @hashbrownai/core@0.8.0 @hashbrownai/react@0.8.0
npm install @hashbrownai/openai@0.8.0
```

</hb-code-example>

Swap `react` for `angular`, and `openai` for your provider.

### 2. Read the extension from `forwardedProps`

Hashbrown sends a standard AG-UI run input plus an object of its own: the response schema for structured output and a flag for generative UI.
Since v0.6, that object rode along as a top-level `hashbrown` key.
AG-UI 1.0 has a proper home for it, `forwardedProps`, the field an agent reads and intermediaries pass through untouched.
A gateway that validates the input strictly can drop a key it does not know.
It can never drop `forwardedProps`.

A v0.8 client sends only the new shape.
If you use an official adapter and never read the extension yourself, step 1 already covered this.
If your server reads it, to pin a schema or pick a model, make this change:

Before:

<hb-code-example header="before">

```ts
const responseSchema = input.hashbrown?.responseSchema;
```

</hb-code-example>

After:

<hb-code-example header="after">

```ts
const responseSchema = input.forwardedProps?.hashbrown?.responseSchema;
```

</hb-code-example>

Deploy the client and the server together.
A server still on v0.7 sees no schema and answers in free text, and it will not tell you why. 😆

### 3. Replace examples with rules

If you pass `examples` to a kit or a UI hook, or build a `system` with the `prompt` template, follow the section above.
Delete the option, describe each component, and write the system prompt as a plain string.

### 4. Move `transformRequestOptions` to the Responses API

If you use the OpenAI or Azure adapter and pass `transformRequestOptions`, rewrite it for `OpenAI.Responses.ResponseCreateParamsStreaming`.
Messages, including system messages, become `input` items, and `max_completion_tokens` becomes `max_output_tokens`.
Both packages raise their `openai` peer dependency to `^6.45.0`.

Before:

<hb-code-example header="before">

```ts
transformRequestOptions: (options) => ({
  ...options,
  max_completion_tokens: 2048,
  messages: [
    { role: 'system', content: 'You are a helpful assistant.' },
    ...options.messages,
  ],
}),
```

</hb-code-example>

After:

<hb-code-example header="after">

```ts
transformRequestOptions: (options) => ({
  ...options,
  max_output_tokens: 2048,
  instructions: ['You are a helpful assistant.', options.instructions]
    .filter(Boolean)
    .join('\n\n'),
}),
```

</hb-code-example>

### 5. Stop expecting activity messages in run input

AG-UI activity messages are display material for the client, and the spec says a client must not send them back to the agent.
Hashbrown now strips them from `input.messages` before each run.
Hashbrown's own providers already ignored them, so this only matters if your server read `role: 'activity'` messages from the run input.
Keep that state on the server, or send it through AG-UI state.

### 6. Handle `role: 'activity'` where you switch on a message role

Most code that switches on `message.role` still type checks.
What breaks is an exhaustive check that assigns the leftover role to `never`, or an `else` branch that assumes the message is from the assistant.
Add an `'activity'` case, even if you ignore it, so an activity is never mistaken for a user or assistant message.

### 7. Expect `id` on user and assistant messages

On input, `id` is optional, and Hashbrown keeps one you supply.
Code that builds messages by hand needs no change.
Code that compares whole message objects, for example tests using `toEqual`, now sees the extra field.
Match on the fields you care about.

The [v0.8 guide for React](/docs/react/migrations/v0-8) and [for Angular](/docs/angular/migrations/v0-8) walks through each step, and ends with a prompt you can hand to an AI coding assistant like Claude Code.

## The Run's Return Value

An AG-UI agent can attach a return value to the event that ends a run.
It is separate from the messages and from shared state.
A LangGraph graph returns its final state.
A workflow returns a summary record.
A judge returns a verdict.

Hashbrown used to drop it.
In v0.8, it is `lastRunResult`:

<hb-code-example header="react">

```tsx
const chat = useChat({ system, transport });

const verdict = chat.lastRunResult;
```

</hb-code-example>

<hb-code-example header="angular">

```ts
readonly chat = chatResource({ system, transport });

readonly verdict = computed(() => this.chat.lastRunResult());
```

</hb-code-example>

A few rules:

1. It is the return value of the last run that completed, as any JSON value, or `undefined` when the agent attached none.
2. It is cleared when the next run starts, so a value always belongs to the messages on screen.
3. Interrupted, cancelled and failed runs never set it.

It is on `useChat`, `useCompletion`, the structured and UI hooks, and every Angular chat and completion resource.
Hashbrown's own provider adapters do not produce one.
Use it with an agent you run yourself.

## Cancelled Runs

AG-UI 1.0 lets a server end a run with `outcome: { type: 'cancelled' }`.
The run was stopped before it completed, and it did not fail.

Hashbrown read that as a malformed interrupt and raised an error.
That was wrong.

In v0.8, a cancelled run settles the same way a local stop does.
The partial answer is rolled back, nothing is retried, and `error` stays empty.
The next message on the thread starts an ordinary new run.

## Conclusion

Decisions give Hashbrown a second kind of model: fast, typed, and built for routing and selection.
UI kits are simpler and more honest without few-shot examples.
The run-input extension sits where AG-UI 1.0 wants it, `lastRunResult` surfaces what your agent returns, and cancelled runs settle cleanly.

That is how this release got better.
